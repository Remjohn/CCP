## 2. Overview

### Problem Statement
Traditional marketing relies on a single "sales sequence," explicitly building excitement for a commercial offer. This transparency immediately activates psychological reactance (resistance to obvious persuasion). 

### Solution
The 72-Hour Identity Anchor Protocol replaces standard warming sequences with a scientifically spaced, 3-day micro-commitment architecture. It anchors the client's identity to the *premise* of the incoming offer without ever explicitly revealing it. By spacing out three interactions over 72 hours, the client infers a stable internal trait ("I am someone who cares about this") rather than external pressure.

### Scope
**In scope:**
- Orchestration of the 3-day (Day -3, Day -2, Day -1) sequence before Day 0 (the conversion event).
- Generation of the specific daily triggers: Observation Prompt, Competence Mirror, and Anticipation Signal.
- Enforcement of strict anti-reactance rules by the `BehavioralScienceGuard`.
- Integration into the FR53 Conversion Sequence pipeline.

**Out of scope:**
- Delivery of the Day 0 actual invitation (handled by FR53 / Coping-Diagnostic Engine).
- Detection of when to start the 72-hours (handled by FR-CBCS-06 SEARCH Phase Engine or Operator trigger).

### Academic Grounding
- **Research Paper:** *Compliance Without Pressure: The Foot-in-the-Door Technique* (Freedman & Fraser, 1966) + *Influence: Science and Practice (Commitment and Consistency)* (Cialdini, 1984) + *The Phenomenon of Psychological Reactance* (Brehm, 1966).
- **Mechanism:** Repeated micro-commitments across time cause the brain to interpret the actions as stable traits ("I am someone who engages with this"). If the actions feel externally coerced (reactance), the effect collapses. The system must remain utterly silent about the impending sale.

### Technical Decisions
- **Anti-Reactance Guard:** Any hint of a sales funnel negates the commitment effect. The `BehavioralScienceGuard` analyzes output and strictly blocks the generation using Regex evaluation.
- **Stateful Sequence:** The protocol relies on a strict SQLite state machine tracking execution to enforce the 24-hour spacing exactly without drifting.

## 4. Implementation Plan

### Stage 1: Protocol Orchestration and Scripting
- **Agent:** `pre-invitation-priming-orchestrator` (Python Generation Script)
- **Inputs:** 
  - `Unified Identity Profile` (DEP-ID: `DEP-ENG-056` — Produced By: FR-CBCS-03)
  - `Change Talk Context` (DEP-ID: `change_talk_archive` — Produced By: FR-CBCS-01)
  - `target_offer_theme` (DEP-ID: `DEP-ENG-053` — Produced By: FR53 Conversion Engine)
- **Outputs:** `PROPOSED: DEP-ENG-059` (72-Hour Trigger Payload Draft).
- **Failure Condition:** If the LLM timeouts or returns malformed multi-part payloads, catch JSONDecodeError, revert state, and re-queue execution.
- **Receipt Chain Guard (DEP-ENG-041):** Cryptographic hash of `client_id` + Draft JSON string written to the audit log BEFORE passing to the Guard gate to prove execution attempt.

### Stage 2: Reactance Prevention Gate
- **Agent:** `BehavioralScienceGuard` (Pi Extension)
- **Inputs:** `PROPOSED: DEP-ENG-059` (Text block arrays parsing Day -3, Day -2, Day -1)
- **Outputs:** `PROPOSED: DEP-ENG-060` (Validation Verdict: PASS / PROVISIONAL / FAIL).

**Quality Gate:** **Reactance Prevention Gate**
- **Triggered when:** Draft generated by the orchestrator attempts to finalize for deployment.
- **Exact Thresholds:**
  - `commercial_flag_count` = `REGEX_COUNT(sequence_text, (buy|offer|tomorrow|special|announce|coming up|get ready|product|program))`
  - `urgent_punctuation_count` = `REGEX_COUNT(sequence_text, (!{2,}|\b[A-Z]{3,}\b))`
- **Verdict - PASS:** `commercial_flag_count == 0` AND `urgent_punctuation_count == 0`. *Downstream Consequence:* Sequence is greenlit and committed to the `72_hour_protocol_logs` database for dispatch.
- **Verdict - PROVISIONAL:** `commercial_flag_count == 0` BUT `urgent_punctuation_count > 0`. *Downstream Consequence:* Draft passes the hard rule but indicates "hype" formatting. Draft is saved to DB but flagged for Operator Review locally on the dashboard (`status = REVIEW_REQUIRED`). Automatic execution pauses.
- **Verdict - FAIL:** `commercial_flag_count > 0`. *Downstream Consequence:* Script blocked entirely. `rewind_generation()` callback triggers the LLM to rewrite explicitly passing the flagged banned words into the negative constraint instructions. Aborts entire protocol after 3 consecutive fails.

### Stage 3: Phased Delivery & Early Abort Resolution Rules
The sequence enforces an early abort rule executed inside the Message Ingestion loop.
- **Variable Resolution Rule (Anti-Reactance Abort):** 
  - IF the system state is currently `D3_SENT` or `D2_SENT`
  - AND the client replies with a message where `liwc_scores.negative_emotion > 0.05` OR `liwc_scores.anger > 0.02` OR `sentiment == 'hostile'`
  - THEN update `status` to `ABORTED`. Apply global 14-day campaign cooldown constraint.

### Stage 4: Resolution Rules for Output Schema
Every field in the `ProtocolSequencePayload` is calculated precisely as follows:
- `sequence_id`: Dynamically generated via `uuid.uuid4()`.
- `client_id` / `coach_id`: Passed synchronously.
- `day_minus_3_script`: Text extraction from LLM parsed JSON array index `0`.
- `day_minus_2_script`: Text extraction from LLM parsed JSON array index `1`.
- `day_minus_1_script`: Text extraction from LLM parsed JSON array index `2`.
- `status`: Resolves to specific Enums based on exact input criteria:
  - `"GENERATED"`: Maps when Stage 2 Gate evaluates == `PASS`.
  - `"D3_SENT"`: Maps IF Telegram API responds `200 OK` for the Day 3 message.
  - `"D2_SENT"`: Maps IF Telegram API responds `200 OK` exactly 24 hours later.
  - `"D1_SENT"`: Maps IF Telegram API responds `200 OK` exactly 48 hours later.
  - `"COMPLETED"`: Maps when the 72-hour window closes and FR53 fires Day 0.
  - `"ABORTED"`: Maps IF the Stage 3 Anti-Reactance Abort rule triggers.
- `abort_reason`: Null by default. IF state == `ABORTED`, maps to String `"Client Resistance Detected"`.
- `last_updated`: `datetime.now(timezone.utc).isoformat()`.

## 8. Acceptance Criteria
- [ ] **AC1 (Anti-Reactance Fail Gate):** A draft script containing the phrase "I have something special to announce tomorrow" returns `commercial_flag_count = 2` ("special", "tomorrow"). MUST be blocked evaluating `isValid: false`, causing immediate LLM regenerative rewrite. **Failure Example:** The system passes the phrasing, triggering client awareness to an incoming sale.
- [ ] **AC2 (Provisional Hype Detection):** A draft containing "I can't wait for you to see this!!" MUST evaluate `urgent_punctuation_count > 0`, routing immediately to `REVIEW_REQUIRED` state instead of blindly sending. **Failure Example:** System bypasses the flag and sends unprofessional, hyper-urgent framing to a premium coaching client.
- [ ] **AC3 (Abort on Resistance):** If `status == D3_SENT` and the client replies with defensive language (`liwc_scores.negative_emotion = 0.08`), the script MUST trigger the Stage 3 resolution rule to `ABORTED` updating `abort_reason = "Client Resistance Detected"`. **Failure Example:** The system ignores the resistance because the webhook loop is disconnected from the state machine, blindly sending Day -2 to an annoyed customer.

## 10. Testing Strategy

### Unit Testing
- Inject 20 strings containing commercial language into the `BehavioralScienceGuard`. Enforce a 100% block rate (FAIL). Inject 5 strings with `ALL CAPS` and `!!!` and ensure 100% PROVISIONAL routing.

### Integration Testing
- Simulate an end-to-end 3-day sequence run locally. Have the synthetic webhook API return `200 OK`. Ensure `status` increments correctly to `D3_SENT` -> `D2_SENT` -> `D1_SENT` -> `COMPLETED`, validating the Python sleep/cron execution timing.

### Safety Testing
- Trigger a protocol run, let D-3 send, and mock a client deletion event. Ensure the state machine trying to transition to `D2_SENT` catches the Postgres `ForeignKeyConstraintError` safely, flipping the queue job to `ABORTED` rather than creating orphaned cron jobs polluting the dispatch queues.
