## Executive Summary: The Visual-Commercial Integration Lockdown

This document extends the CBAR stress-testing methodology — previously applied to the FR-VID video pipeline (9 specs) and Phase 4 CCP Studio (Capability Area 11) — into the **Visual Control Layer (Track A)** and the **Commercial Intelligence Layer (Track B)**. These two tracks represent the first production-grade formalization of the platform's AI generation capabilities and its SaaS commercial skeleton. They do not exist in isolation: a coaching client enrolled through the Telegram bot will immediately consume Identity LoRA renders, ConsciousSmile expression outputs, and First Frame Composer assets. A billing event will gate every one of those renders. An admin action will arbitrate disputed outputs.

The questions below apply CBAR's 4-part anatomy — Tension, Failure Scenario, Resolution Demand, Downstream Proof — to the nine most dangerous architectural intersections across all eight specs. A system that cannot resolve these questions deterministically before implementation begins will produce billing leakage, visual identity drift, cascade pipeline failures, and broken coach tenant isolation. The resolutions below constitute the **Architectural Decision Log** for all downstream build gates.

## BLOCK A — Visual Identity Integrity

### **Q1. LoRA Identity Drift vs. ConsciousSmile Expression Override: A coach's Identity LoRA (FR-VIS-17) is trained on reference photos where the coach's natural resting expression is a slight, closed-mouth smile — a defining brand characteristic. When the ConsciousSmile Adapter (FR-VIS-14) receives a generation request with `expression_channel: JOY` at `intensity: 0.9`, it applies a full 28-channel FACS override that opens the mouth wide, raises the cheeks dramatically, and crinkles the eyes. The resulting image is technically a correct `JOY` expression — but the coach no longer looks like themselves. Which system controls facial identity, and what prevents ConsciousSmile from overwriting the Identity LoRA's learned facial geometry?**

The tension is between two architectural mandates that are both individually valid: FR-VIS-17's Identity LoRA is the canonical source of truth for the coach's visual identity, enforcing likeness fidelity as the non-negotiable first constraint; and FR-VIS-14's ConsciousSmile Adapter is authorized to write FACS channel values that physically alter the face to achieve the prescribed emotional register. At full intensity, these two mandates geometrically conflict — the adapter overwrites the LoRA's embedded facial structure, producing an expression that is correct on a generic human, but wrong on this specific coach.

This conflict, if unresolved before the rendering stage, will produce a generation where the coach's facial geometry is technically accurate at `t=0` (LoRA base), but then distorted by the FACS override during the diffusion sampling steps. The First Frame Composer (FR-VIS-16) — which receives this combined output and assembles the final scroll-stop frame — will embed a face that passes the ConsciousSmile quality gate but fails the implicit identity coherence check. Downstream: every social asset published from that First Frame will feature a face that coaches' audiences will not recognize as authentic.

The resolution is the **Identity-Expression Layering Hierarchy**, derived from the dependency order established across FR-VIS-14 and FR-VIS-17: the Identity LoRA fires first, at full weight, establishing the coach's geometric anchor. The ConsciousSmile Adapter is prohibited from operating on raw latent space — it exclusively operates on the LoRA's already-stabilized output by injecting FACS delta vectors, not by replacing base features. This is enforced by capping the ConsciousSmile ControlNet conditioning weight to a maximum of **0.75** when an Identity LoRA is present in the generation session, regardless of the requested intensity. The `intensity: 0.9` request is automatically normalized to `effective_intensity: 0.675`, preserving the JOY register while anchoring the facial geometry to the LoRA's learned structure. The `expression_preset_id` stored in the downstream `first_frame_specs` table must log both the requested and effective intensity values for audit traceability via DEP-ENG-041.

### **Q2. ConsciousPose Arm Extension vs. Frame Boundary Safety: The ConsciousPose Library (FR-VIS-15) contains atom `CP-ARM-OPEN-LOW-BILATERAL` — both arms extended outward at 45° to the body at hip height. This is the canonical "invitation" pose for community-building content. The First Frame Composer (FR-VIS-16) receives a composition request for a 9:16 vertical story frame at 1080×1920 pixels. The coach's Identity LoRA bakes in a shoulder width that, when combined with the bilateral arm extension, will push both hands outside the safe-zone boundary of the frame. Does the system render the crop silently, truncate the wrists, or trigger a gate failure?**

The tension is between FR-VIS-15's atomic pose library — which defines `CP-ARM-OPEN-LOW-BILATERAL` as a clinically valid compositional unit whose behavioral meaning depends on the full arm extension being visible — and FR-VIS-16's Format Adapter, which enforces `safe_zone_margin: 80px` at all frame edges as an inviolable composition rule. Both constraints are correct in isolation. Combining them produces a geometrically impossible composition: the pose is meaningless without the hands, and the format is invalid without the margin.

If unresolved, the ComfyUI sampler will silently render the image with the hands clipped at the frame edge. The pose atom's communicative value — conveying "openness" and "invitation" — is destroyed. The audience reads truncated wrists as a framing error, not an intentional gesture. The First Frame Composer's quality gate scores this as a passed composition (no margin violation detected because the hands are technically outside the margin). The error propagates invisibly through the pipeline, appearing only when a human reviews the final asset.

The resolution is the **Pose-Format Pre-Validation Gate**, executed in FR-VIS-16's Stage 1 *before* the ComfyUI pipeline is invoked. When the FFC receives a pose atom from the ConsciousPose library, it calculates the projected bounding box of that atom against the target format dimensions and the coach's LoRA-derived shoulder width. If the projected bounding box exceeds the safe-zone boundary, the system does **not** silently clip — it executes one of three deterministic fallbacks in priority order: (1) Automatically substitute the closest safe-zone-compliant pose atom from the same semantic cluster (e.g., `CP-ARM-OPEN-LOW-SINGLE-RIGHT` for single-arm invitation); (2) If no safe substitute exists, scale the subject's body slightly smaller within the frame to create natural arm room; (3) If scaling produces a proportion violation, escalate to the Factory Floor review queue (FR-COM-02) with a `gate_reason: POSE_BOUNDARY_OVERFLOW` flag. The FFC must log which fallback was invoked in the `first_frame_specs.pose_override_log` field for Receipt Chain Guard accountability.

### **Q3. Identity LoRA Training Data Contamination vs. ConsciousSmile CFED Dataset: FR-VIS-17 requires 30–60 coach reference photos as training input for the Identity LoRA. FR-VIS-14 defines the CFED Dataset (DEP-VIS-013) as the academic source of ground-truth FACS channel mappings used to train the ConsciousSmile Adapter. A coach's reference photo set submitted for LoRA training contains 12 images sourced from professional photoshoots where the coach's expressions were heavily stylized — exaggerated smiles, theatrical wide-eyed looks — that do not match the FACS-neutral reference standard required by CFED. What happens when the LoRA trained on these photos is combined with the ConsciousSmile Adapter, and how does the system detect and resolve trainingset contamination before it propagates?**

The tension is between FR-VIS-17's permissive dataset acceptance policy — which allows any coach reference photos that pass the technical quality gates (resolution, face detection, framing) — and FR-VIS-14's strict requirement that the ConsciousSmile Adapter's base facial state represent a FACS-neutral resting expression (Action Unit scores near zero across all 28 channels). When a LoRA is trained on heavily styled expressions, the model's learned "neutral" face is actually a biased toward the coached expressions in the training photos. Applying ConsciousSmile deltas on top of this biased neutral produces expression doubles — the JOY delta stacks on top of a training-set JOY bias, producing a grotesque overexpression that no longer maps to any human FACS reference.

The downstream failure occurs in FR-VIS-16's First Frame Composer, which inherits the combined output. The FFC's quality gate metrics — scoring composition, expression register, and brand coherence — will each independently pass, because the expression is technically "strong JOY" and the composition rules are not violated. The error is invisible to all automated gates. The contaminated LoRA becomes the canonical identity artifact for all future renders until a human reviewer notices the uncanny expression drift weeks or months later.

The resolution is the **FACS Neutrality Pre-Screen** integrated into FR-VIS-17's Stage 1 (Dataset Curation). Before any reference photo is accepted into the LoRA training queue, it must pass a mandatory FACS neutrality scan using the same 28-channel Action Unit detector that FR-VIS-14 uses for expression classification. Photos where any combination of AUs exceeds a total expression score of **0.35** (on a 0-1 normalized scale) are flagged as "expression-biased" and routed to one of two outcomes: (1) The photo is excluded from training if the coach has 30+ qualifying neutral photos remaining — the system trains on the clean subset; (2) If exclusion would reduce the training set below the 30-image minimum, the system triggers an alert to the coach's AFFiNE workspace requesting reshoots, and **pauses the LoRA training job** until compliant photos are submitted. Under no circumstances is an expression-contaminated LoRA permitted to reach the EFS deployment stage. This gate writes its audit result to the Receipt Chain Guard (DEP-ENG-041) before any training compute is allocated.

## BLOCK B — Billing & Generation Gate

### **Q4. Billing Jail vs. Scheduled Check-In Delivery: A coach's Stripe subscription enters `past_due` status at 11:47 PM on a Tuesday night. Their Redis permission cache (FR-COM-01) is updated to `status: past_due` within 60 seconds of the Stripe webhook firing. However, 14 of their CBCS clients are scheduled to receive their Wednesday 6:00 AM check-in message — a message that was composed by the CMF pipeline 18 hours earlier, written to the queue, and is now sitting in the Telegram dispatch buffer. At 6:00 AM, the dispatcher fires. The billing middleware reads `status: past_due` from Redis. Do the 14 check-ins send or not?**

The tension is between FR-COM-01's Jail System — which mandates that any platform action reading Redis status `past_due` must be blocked immediately and unconditionally — and the CBCS pipeline's ethical obligation to clients who enrolled in good faith, whose check-in messages were already paid for in the previous billing cycle, and whose therapeutic relationship with their coach will be silently broken if messages are dropped without notice. Both constraints reference valid business and ethical principles. The billing middleware cannot selectively apply the jail based on historical payment status; it reads only the current state.

If the jail blocks unconditionally at 6:00 AM, 14 clients receive no check-in, no error message, and no explanation. The coaching relationship fractures silently. The coach — who is asleep at 6:00 AM, unaware of the billing failure — wakes to 14 confused clients, not a billing alert. This is the worst possible product experience: billing failure harms the end-client, not just the coach-operator who failed to pay.

The resolution is the **Billing Isolation Principle with Client Grace Window**, formalized as a new constraint in FR-COM-01. The Jail System blocks all *new* pipeline actions: new content generation requests, new LoRA renders, new enrollment activations. It does **not** retroactively block pre-queued client-facing messages that were scheduled during an `active` billing period. The dispatcher must carry a `billing_period_scheduled` timestamp on every queued message. If the Redis status is `past_due` at dispatch time, the middleware checks this timestamp: if the message was scheduled *before* the billing failure timestamp (stored in `billing_events` table), it dispatches without blocking and logs a `GRACE_DISPATCH` event in the billing audit trail. The coach receives a separate AFFiNE notification at the moment of grace dispatch: "⚠️ 14 check-ins sent under grace window. Your subscription is past due. Clients may not receive further messages unless payment is resolved within 24 hours." This preserves client trust, documents the billing exception, and provides the coach a hard deadline.

### **Q5. Stripe Metered Billing vs. First-Message Trigger Race Condition: A coach has 6 clients enrolled via the Telegram Onboarding Agent (FR-COM-03). The CBCS engine is configured to send all 6 clients their first check-in message at 8:00 AM Monday simultaneously. FR-COM-01's billing architecture mandates that the $4 CBCS credit is reported to Stripe at the exact moment the first message is sent to each client. The Stripe Metered Usage API is rate-limited to 100 requests per second. If 1,000 coaches each have 6 clients receiving first messages in the same Monday morning spike window, the system attempts to make 6,000 Stripe API calls simultaneously. How does the architecture guarantee that billing is reported for every client without hitting rate limits, without double-charging, and without sending a message before billing is confirmed?**

The tension is between FR-COM-01's billing atomicity requirement — the $4 usage report to Stripe must be confirmed before the client message is sent, to prevent the "send-then-forget" billing exploit — and the physical constraint of Stripe's API rate limit, which will reject requests beyond the 100/sec threshold, causing billing reports to fail, which will then cause message dispatch to block, which will cause thousands of clients' first check-ins to be silently delayed or dropped.

If unresolved, the 8:00 AM Monday spike produces a cascade: Stripe rate-limits the billing middleware, the billing middleware returns an unresolved status to the CBCS dispatcher, the dispatcher — following the atomicity rule — holds all 6,000 first messages, and thousands of clients experience a silent first-message failure. The coaches receive no notification. The billing events are partially recorded. The audit trail is incomplete. The Receipt Chain Guard (DEP-ENG-041) has no record of which clients were billed and which were not.

The resolution is the **Metered Billing Queue with Exponential Backoff**, replacing the synchronous Stripe call with an asynchronous pre-billing architecture. When a first-message event is imminent (T-30 minutes before scheduled dispatch), the CBCS engine pre-submits billing reports to an internal `billing_queue` table with status `pending`. A dedicated billing worker — rate-limited at 80 requests/sec (20% below Stripe's limit for headroom) — drains this queue and reports usage to Stripe, updating each row to `billed` upon confirmation. The CBCS dispatcher is forbidden from sending the first client message until the corresponding `billing_queue` row shows `status: billed`. If a billing confirmation is not received within 5 minutes of the scheduled dispatch time, the dispatcher defers the message by 5-minute intervals (up to 30 minutes) before escalating to the Factory Floor (FR-COM-02) as a `BILLING_GATE_TIMEOUT` alert. The pre-billing window also guarantees idempotency: each `billing_queue` row carries a unique `idempotency_key` derived from `(coach_id + client_id + message_scheduled_at)`, preventing double-charges if the billing worker retries a failed row.

## BLOCK C — Admin Dashboard & Pipeline Orchestration

### **Q6. Factory Floor Approve Action vs. ComfyUI Re-Render Lock: An operator in the Global Admin Dashboard (FR-COM-02) reviews a First Frame Composer output in the Factory Floor queue. The FFC generated the asset 4 hours ago; the coach's Identity LoRA has been re-trained and redeployed to EFS in the intervening period (a scheduled weekly LoRA refresh under FR-VIS-17). The operator approves the asset. Does the system deliver the 4-hour-old asset to the coach — rendered with the previous LoRA version — or does it automatically trigger a re-render with the new LoRA before delivery?**

The tension is between FR-COM-02's Factory Floor authority model — where an operator's Approve action is a final, unambiguous directive to deliver the asset immediately — and FR-VIS-17's LoRA versioning contract, which guarantees that all delivered visual assets reflect the coach's current canonical identity (the latest deployed LoRA on EFS), not a snapshot from a previous rendering cycle. A LoRA refresh is a material change to the coach's visual identity anchor. Delivering stale renders silently violates FR-VIS-17's identity consistency guarantee.

If the stale render is approved and delivered, the coach receives an asset that does not match their current Identity LoRA profile — their hair, facial geometry, or other learned features may have been corrected or updated. The coach publishes the asset, their audience sees a face that doesn't match their other current content, and the platform's identity consistency promise is broken. Worse: the `identity_lora_registry` table shows the current LoRA version, but the delivered asset carries metadata pointing to the previous version — a silent provenance mismatch that the Receipt Chain Guard will not catch because no single pipeline stage "lied."

The resolution is the **LoRA Version Lock Check at Approval Time**. The Factory Floor does not treat Approve as a direct delivery trigger. Instead, it fires a pre-delivery validation step: the system queries `identity_lora_registry` for the coach's current active LoRA version ID, then compares it to the LoRA version ID embedded in the asset's `first_frame_specs.lora_version_id` metadata. If they match, delivery proceeds immediately. If they do not match — meaning the LoRA was updated after the asset was rendered — the system presents the operator with a version conflict dialog: "⚠️ This asset was rendered with LoRA v2.1. Current version is v2.3. Approve stale version or trigger re-render?" Re-render queues a fresh ComfyUI job with the current LoRA and returns the new asset to the Factory Floor for review. The operator's approval action, the version mismatch, and the resolution (stale-approved or re-rendered) are all written to the `admin_actions` table and the Receipt Chain Guard (DEP-ENG-041).

### **Q7. Program Full Capacity vs. Admin Override Enrollment: A coach's "90-Day Transform" program (FR-COM-04) has `max_clients: 30` and `current_enrolled: 30`. The Program Registry (DEP-COM-009) correctly returns `{"valid": false, "reason": "PROGRAM_FULL"}` to any new Telegram enrollment attempt. However, an operator in the Global Admin Dashboard (FR-COM-02) receives a support ticket from a coach who wants to manually add one VIP client — their most important client — as client #31, bypassing the capacity limit. The admin uses the Factory Floor to trigger a manual override enrollment. Which system has authority over client capacity — the Program Registry's deterministic gate, or the admin's manual override — and what are the downstream consequences for billing?**

The tension is between FR-COM-04's capacity enforcement contract — which is not merely a suggestion but a hard operational promise, since coaches design their program delivery (check-in schedules, content calendars, personalisation depth) around a specific client count — and FR-COM-02's admin override authority, which exists precisely to handle exceptional edge cases that automated systems cannot anticipate. Both authorities are legitimate within their domain. The conflict is who takes precedence when they collide.

If the admin override silently adds client #31 without updating the program's capacity logic, the Program Registry continues to report `current_enrolled: 30`, the billing system counts 30 CBCS clients for Stripe usage reporting, and the coach's content calendar generates 30 check-in schedules. Client #31 receives the Telegram enrollment confirmation, but the backend has no scheduled check-ins, no billing record, and no AFFiNE workspace card for them. They are a ghost client — enrolled in name only.

The resolution is the **Admin Override Enrollment Protocol**, a formal multi-step action that the Factory Floor must execute atomically when a capacity override is requested. The operator is not permitted to simply "add a client" — the override must: (1) Increment `max_clients` by 1 in `coaching_programs` for the specific program (not suppress the check); (2) Provision the client through the same full auto-provisioning sequence as FR-COM-03 (CBCS profile → Stripe billing report → AFFiNE workspace card → scheduled check-ins); (3) Write an `admin_actions` row with `action_type: capacity_override` and the operator's rationale notes; (4) Write the override event to the Receipt Chain Guard (DEP-ENG-041). The override is not a bypass — it is a structured expansion. The coach receives an AFFiNE notification: "Admin manually enrolled 1 additional client. Your program capacity has been temporarily expanded to 31." This ensures billing, provisioning, and audit trails are complete regardless of origin.

## BLOCK D — Cross-Layer Data Integrity

### **Q8. Profiles Table Collision vs. Telegram Re-Enrollment: In the post-audit architecture, FR-COM-03 enrolls new clients by inserting into the core `profiles` table with `telegram_user_id` as a UNIQUE-constrained column. A client successfully enrolls in Coach A's "90-Day Transform" program using their Telegram account. Six months later, they purchase a completely different program from Coach B's "Mindset Reset" — a different coach, a different program, a different CBCS relationship. When the Telegram Onboarding Agent fires `INSERT INTO profiles`, the database raises a `UNIQUE CONSTRAINT` violation on `telegram_user_id`. The client is blocked from enrolling with Coach B. How does the architecture support one Telegram user participating in programs from multiple coaches without violating the unique constraint or creating duplicate profiles?**

The tension is between the database constraint that was introduced to fix the FR-COM-03 audit finding — `telegram_user_id BIGINT UNIQUE` on the `profiles` table ensures deduplication within a single coaching relationship — and the multi-coach business model of the platform, where one client may legitimately engage multiple coaches sequentially or simultaneously. The UNIQUE constraint, designed as a safety mechanism, has become an architectural blocker for a valid and expected user journey.

If unresolved, the second enrollment attempt raises a silent 500 error in the Onboarding API. The client receives no explanation — the Telegram bot times out with a generic error message. Coach B never receives a notification. The client assumes the system is broken and does not re-attempt. The platform has structurally prevented a valid commercial transaction.

The resolution is the **Multi-Enrollment `profiles` Architecture**, requiring a schema correction to the post-audit design: `telegram_user_id` must be moved from a `UNIQUE` constraint on `profiles` to a `UNIQUE` *composite* constraint on `(telegram_user_id, coach_id)`. This permits one Telegram user to have distinct profile rows for each coach they engage, while still preventing duplicate enrollments *within* the same coaching relationship. The auto-provisioning sequence in FR-COM-03's Stage 3 changes from `INSERT INTO profiles` to `INSERT INTO profiles ... ON CONFLICT (telegram_user_id, coach_id) DO UPDATE SET status = 'active', enrolled_at = NOW()` — allowing re-enrollment after a previous completion or drop. The Migration 005 `ALTER TABLE profiles` statement must be updated to replace `UNIQUE (telegram_user_id)` with `UNIQUE (telegram_user_id, coach_id)`. This correction must be applied to Migration 005 before execution.

### **Q9. Campaign Funnel Conversion Tracking vs. Coach Tenant Isolation: FR-COM-04 generates a static funnel one-pager for each campaign, hosted at `{slug}.conscious.co/{campaign}`. This page displays the coach's headshot, program description, and a Telegram bot CTA. FR-COM-02's Global Admin Dashboard aggregates funnel analytics — tracking `total_funnel_views` and `conversion_rate` across all coaches for platform-level performance monitoring. A visitor lands on Coach A's funnel page. How does the system track that view — attributing it to Coach A's campaign for analytics — without the Admin Dashboard's aggregation query violating ADR-01's coach tenant isolation constraint, and without the static S3 page having access to the Supabase auth layer required to enforce RLS?**

The tension is between ADR-01's mandatory coach isolation — data belonging to Coach A must not be accessible to Coach B's authenticated session, and RLS is the enforcement mechanism — and the Admin Dashboard's architectural requirement to aggregate view data across all coaches using `service_role` keys, which bypass RLS, which means the Dashboard effectively has access to all coaches' campaign data simultaneously. The funnel tracking creates a third complication: the static S3 page has no Supabase auth context, so it cannot enforce RLS even if RLS existed at the tracking layer.

If unresolved, the analytics tracking architecture has two failure modes: either funnel views are tracked in Supabase by the static page calling an unauthenticated API endpoint — creating a surface for fabricated view inflation by any actor who discovers the endpoint — or the Admin Dashboard uses `service_role` queries that pull all coaches' funnel data into a shared dashboard table, creating a data residency violation where Coach A's conversion data is technically co-located with Coach B's in the same query result set.

The resolution is the **Event-Sourced Funnel Analytics Architecture**. The static funnel page fires a server-side `POST /api/analytics/funnel-view` event to an authenticated edge function, passing only the `campaign_id` from the page's metadata (embedded at S3 generation time). The edge function is unauthenticated at the client level but validates the `campaign_id` against a signed token generated at funnel-page-generation time — preventing spoofed view inflation. The function writes only to an `analytics_events` table with `coach_id` and `campaign_id` populated from the server-side `campaign_id` resolution, maintaining RLS-compatible row ownership. The Admin Dashboard's aggregation query operates via `service_role` on a **materialized view** — `mv_campaign_analytics` — that pre-aggregates the data into platform-level metrics (total views, conversion rate) with `coach_id` removed from the output schema. The materialized view is the firewall: the Dashboard sees platform aggregates, never raw per-coach rows. Individual coaches see their own rows through the standard RLS-enforced `campaigns` table. Coach isolation is preserved at both the query and data residency layers.

## FINAL VALIDATION CONCLUSION: VISUAL CONTROL + COMMERCIAL INTELLIGENCE LAYER

The eight specifications forming Tracks A and B pass the CBAR adversarial stress test. Nine cross-spec tensions were identified spanning identity-expression geometry, pose-format boundary conflicts, LoRA training contamination, billing grace windows, rate-limit race conditions, admin override authority, multi-enrollment schema constraints, and analytics privacy isolation. Each tension has been resolved with a named, deterministic architectural mechanism.

**The Architectural Decision Log, extracted from the nine resolutions above, mandates the following amendments prior to Phase 0 implementation:**

1. **ConsciousSmile ControlNet weight cap:** Maximum 0.75 when Identity LoRA is active. Log effective vs. requested intensity in Receipt Chain Guard.
2. **FFC Pose-Format Pre-Validation Gate:** Bounding box check before ComfyUI invocation. Three-level fallback: atom substitute → scale → Factory Floor escalation.
3. **FACS Neutrality Pre-Screen in FR-VIS-17:** AU score threshold 0.35 before LoRA training begins. Pause job if training set falls below 30 compliant images.
4. **CBCS Client Grace Window:** Pre-queued messages from `active` billing period dispatch under grace window. Coaches notified at grace dispatch time.
5. **Metered Billing Queue:** Asynchronous pre-billing 30 minutes before first-message dispatch. Idempotency key on every billing queue row. 5-minute retry with 30-minute escalation ceiling.
6. **LoRA Version Lock at Factory Floor Approval:** Version ID comparison before delivery. Operator dialog required on mismatch. All paths logged to Receipt Chain Guard.
7. **Admin Override Enrollment Protocol:** Capacity expansion + full provisioning sequence + `admin_actions` audit row. Not a bypass — a structured expansion.
8. **Multi-Enrollment Schema Fix:** Change `UNIQUE (telegram_user_id)` to `UNIQUE (telegram_user_id, coach_id)` in Migration 005 before execution.
9. **Event-Sourced Funnel Analytics:** Signed campaign token validation at edge function. Materialized view `mv_campaign_analytics` strips `coach_id` before Dashboard aggregation.

**Tracks A and B are formally validated for Phase 0 implementation.**
