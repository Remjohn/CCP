# Product Requirements Document (PRD): The Sovereign Telegram Mini App Ecosystem

## 1. Documentation Preamble & Scope Definition
*Written by Paige, Technical Documentation Specialist.*

This document translates the strategic mandates established in `CCP_Update_Product_Brief.md` into strict, buildable engineering requirements. Our goal here is clarity, precision, and adherence to established documentation standards. 

**The Brownfield Constraint:** The systems we are building today must sit adjacent to, and interface directly with, the existing Capability Area 11 (CA11), specifically updating Section 4.5 (`CCP Studio Platform`) and Section 4.4 (`Interactive Trivianar Engine`) of the `prd-update-CA11-quad-platform.md` document. We are *migrating* delivery protocols (from Webhooks to WebSockets) and *encapsulating* visual layers (from Telegram Chat to Native Mini App), but we are **not** rewriting the underlying Neo4j `Context_Premise` logic or the CPSC (Conscious Persuasion Sales Cycle). Any data generated by these new Mini Apps must strictly conform to the existing database schemas defined in `prd.md`.

This PRD defines four primary engineering features:
1. The B2B2C Coach-Pays Onboarding Architecture.
2. The Telegram Mini App UI/UX Paradigm (Split-Screen Native Video & Canvas).
3. The WebRTC Roleplay Engine (2-Human + 1-AI Moderator).
4. The Interactive Trivianar Engine Migration.

## 2. Feature Definition 1: The B2B2C Freemium Architecture

### 2.1 Overview
The CCP is transitioning from traditional high-ticket SaaS onboarding to a low-friction, high-velocity "Audit-First" flywheel. The objective is to convert external coaches into a metered billing architecture (Coach-Pays model) based entirely on the lead generation capacity we provide them via their own viral funnels.

### 2.2 Requirements: The Coach-Pays Conversion Flow
**Req-1.1 (Trial Initiation & Meter Trigger):** When a coach's client (the end-user) completes their free voice assessment and explicitly opts into the 7-day challenge trial, the `coach_id` Stripe subscription is metered exactly `1.90 USD` for that trial user lead. The user themselves pays the coach directly via the coach's own integrations, not via CCP.
**Req-1.2 (Provisioning Trigger):** When a guest coach gets acquired via the B2B Viral loop, the Guardian Agent must trigger the backend generation of the Coach's isolated AFFiNE workspace (FR-CA11-01) for free, capturing their Stripe details for future metered billing without an upfront SaaS charge.
**Req-1.3 (Trial Expiration State):** At T+168 hours (7 days) of an end-user's trial, if that user converts to being a paid client of the coach, the system transitions that user's status and hits the coach's Stripe meter for the base `3.90 USD` active client seat.

### 2.3 Requirements: The Maximum Export Logic (No Compute Billing)
**Req-2.1 (Client Capacity Metering):** The primary revenue engine is tied to the CBCS (Telegram Invisible Coaching App). For every unique `client_id` associated with a `coach_id` that logs more than 1 interaction in a billing cycle within the `cbcs_interaction_logs` table, the system must emit a Stripe Usage Record of `3.90 USD` for that month.
**Req-2.2 (The Strict Weekly Cap):** Engineering must NOT build a "compute margin" billing system. The SVRE limits are enforced programmatically. Every Coach is granted exactly 4 exports per week per Content Format, AND a strict global limit of 8 total exports per week across all formats combined. There are 8 total formats: Shorts Videos (Reels), Long Videos (Tier List/Reactions), Long Carousels (Storytelling/Listicles), Short Carousels (up to 5 slides), MEMEs, Polls, Hot Takes, and Super Visuals.
**Req-2.3 (Limit Reset):** A scheduled CRON job (`reset_export_limits.py`) must reset all Redis counters tracking these 8 formats back to 0 every Sunday at 23:59 UTC.

### 2.4 Requirements: The Customer Journey Dashboard & Resource Portal
**Req-3.1 (Stripped Utility):** The coach's AFFiNE workspace must be radically simplified. It must only display the list of their connected users and their direct psychological/performance data.
**Req-3.2 (Telemetry View):** The dashboard must render the specific user's performance, completion tracking, a visual Mood Bar, and allow the coach to directly read or listen to submitted journal entries. 
**Req-3.3 (Rule-Based Resource Allocation):** Coaches do NOT manually assign resources to individuals. The UI must feature an asset provisioning area where coaches upload videos/PDFs and assign them purely to conditional Tags or Segments.
**Req-3.4 (Agent Proactive Tracking):** The Agent network must autonomously monitor user behavior and assign demographic/behavioral tags dynamically, thereby automatically unlocking matching resources.
**Req-3.5 (Client Resource Portal Cadence):** The Telegram Mini App frontend must contain a "Resource Portal" natively accessible to the client. Because the challenge requires active participation 5-6 days per week, the Guardian Agent must dynamically prompt the user on the 1-2 "empty" buffer days to log into this portal to revise and study their unlocked assets.

## 3. Feature Definition 2: The Telegram Mini App UI/UX Paradigm

### 3.1 Overview
The execution of complex synchronous scenarios inside a standard Telegram text chat is structurally impossible. We are upgrading the Telegram "Nervous System" by deploying Telegram Mini Apps initialized via the `WebApp` API. This allows us to run standard React JS/HTML5 canvases on top of the Telegram client without requiring the user to open Safari or Chrome.

### 3.2 Requirements: The "Debate Format" Split-Screen UX
**Req-4.1 (Viewport Lockdown):** The React frontend must capture the Telegram `window.Telegram.WebApp` object. It must immediately invoke `expand()` to force full vertical screen height. It must invoke `disableVerticalSwipes()` to prevent the user from accidentally dismissing the Mini App during a live roleplay or Trivianar.
**Req-4.2 (Dual-Video Co-Hosting):** Trivianar is strictly a Debate format. The Top 40% of the screen must support Dual Native Telegram Video Chat streaming (Side-by-Side) for the two Co-Hosts leading the debate. 
**Req-4.3 (Native Stream Recording):** The Mini App WebRTC bridge must actively record the video streams of both co-hosts into an S3 bucket for internal interaction logging and AI Moderator review. (Note: SVRE automated video editing is strictly reserved for the Coach's Daily Mini App Recordings, not live WebRTC streams).
**Req-4.4 (Bottom HTML5 Canvas):** The bottom 60% of the viewport displays the React app. This area renders the Trivianar buttons (A/B/C/D), the live audience voting leaderboards, and the particle confetti generators.

### 3.3 Requirements: UI/Visual Standards
**Req-5.1 (Dark Mode Enforcement):** Ensure the application strictly adheres to the `themeParams` provided by the Telegram WebApp API. If `color_scheme` is dark, the background must snap to `#1C1C1E`.
**Req-5.2 (High-Contrast Buttons):** All interaction nodes must carry highly visible border-box styling. "Active" or "Selected" states during Trivia must be immediately visually distinct (e.g., snapping from `#333333` to `#FFD700` with a 150ms ease-out transition).
**Req-5.3 (WebSockets Loading State):** Because WebRTC and WebSocket negotiations take 400-800ms, the application must never display a blank screen. A continuous, branded Skeleton Loader must bridge the gap between `DOMContentLoad` and the `SOCKET_CONNECTED` event.

## 4. Feature Definition 3: The 2-Human + 1-AI Roleplay Engine

### 4.1 Overview
The most aggressive product paradigm we are shipping is the Coach-to-Coach Roleplay Engine. Designed as our B2B viral sink, it forces coaches to practice synchronous objection-handling via Daily.co WebRTC connections. The third party in this connection is an AI Moderator powered by the FR61 Jim Rohn Voice architecture.

### 4.2 Requirements: WebRTC Peer-to-Peer Instancing
**Req-6.1 (Daily.co Room Generation):** When a coach clicks "Initiate Roleplay" in their Coach Dashboard, the backend must generate a time-limited `daily.co` meeting room URL via their REST API. 
**Req-6.2 (The Viral Invitation Link):** The system must generate a universally accessible Deep Link (e.g., `https://t.me/CCPBot/RoleplayApp?startapp=ROOM_ID`). The coach sends this Deep Link to their peer.
**Req-6.3 (Guest Join Pipeline):** When the external peer clicks the link, Telegram opens the Mini App automatically. They are prompted for Camera/Mic permissions via the standard Browser API, and injected into the Daily.co WebRTC token-gated room. No account creation is requested at this stage to preserve the zero-friction entry.

### 4.3 Requirements: The AI Moderator Specifications
**Req-7.1 (Pipecat Orchestration):** The AI Moderator must be connected to the Daily.co room via a headless Pipecat worker. It operates utilizing Nvidia NIM Whisper STT → Llama-3/Gemma-4 reasoning → ElevenLabs/Nvidia Riva TTS. 
**Req-7.2 (Roleplay Tracking Protocol):** The AI Moderator is not a participant in the Roleplay; it is the judge. The backend must enforce the `Mood State Resonance` rules outlined in `prd.md`. The AI must track:
- Interrupt frequency between the two humans.
- Pacing/WPM (Words Per Minute).
- Objection handling success based on the loaded "Scenario Brief" (e.g., High-Ticket Price Resistance).
**Req-7.3 (Biometric Feedback Delivery):** At the conclusion of the drill, the AI Moderator's audio channel un-mutes, and it delivers a 60-90 second surgical critique based solely on the data collected in Req-7.2.

### 4.4 Requirements: The Scarcity Stop & Pre-Qualification Gate
**Req-8.1 (Artificial Scarcity Timer):** The React frontend must render a prominent, declining "Energy Bar" or visual timer tracking exactly 24 minutes (1,440 seconds).
**Req-8.2 (The Hard Stop Procedure):** The 24-minute limit is absolute. At `T - 20 seconds`, the AI Moderator must interrupt the room with a standard exit phrase: *"Excellent session. The speaking audit is concluding."* 
**Req-8.3 (Room Destruction):** At precisely `T = 24:00`, the FastApi backend must execute a `DELETE` request against the Daily.co room API. The WebRTC connection must be severed unconditionally for all participants.
**Req-8.4 (The Pre-Qualification Prompt):** Only after the room is destroyed, the Guest Coach is presented with three strict qualification questions in the React App: 
1. Are you a coach/consultant? 
2. Do you have an audience? 
3. Do you want to run challenges?
**Req-8.5 (The Challenge Funnel):** If the user answers YES to the criteria, they are formally invited to join the "Speaking Audit Law 28 Challenge" to fully review the AI's analysis of their performance. If they answer NO, they receive a polite rejection state and the flow terminates.

## 5. Feature Definition 4: The Trivianar Broadcast Engine

### 5.1 Overview
The migration of the existing Interactive Trivianar Engine (FR-CA11-19) from a heavily congested Telegram Chat interface into the sleek Mini App interface.

### 5.2 Requirements: WebSockets over Webhooks
**Req-9.1 (The Protocol Shift):** Previously, trivia button presses were sent as `callback_queries` to the Telegram Bot API Webhook. This resulted in devastating Rate Limit (429) errors at scale. All interactive elements in the Mini App Trivianar must communicate via persistent WebSockets directly to the FastAPI server (`wss://api.consciouscoaching.com/v1/trivianar`).
**Req-9.2 (Event Broadcasting):** The instructor's dashboard triggers events (e.g., `START_QUESTION`, `REVEAL_WINNER`). The FastAPI server must broadcast these events instantaneously down the open WebSocket connections to all connected Mini App clients, bypassing Telegram entirely. 

### 5.3 Requirements: State Synchronization & Queueing
**Req-10.1 (High-Concurrency Redis Queueing):** In a 5,000-user Trivianar, a single question will generate 5,000 WebSocket payload responses within a 4-second window. The FastAPI server must **not** attempt `INSERT` operations into PostgreSQL synchronously.
**Req-10.2 (The LPUSH Method):** The server must utilize `LPUSH` into a Redis queue (e.g., `trivianar:responses:Q_ID`). A background Celery worker will drain this queue, writing bulk inserts into the `trivia_responses` table every 500ms.
**Req-10.3 (Continuous Leaderboard):** The React frontend holds local state (`score`). When the background worker successfully processes the answer, it emits a `SCORE_CONFIRMED` event down the specific user's WebSocket, updating their UI without causing a database lock.

## 6. Behavior-Driven Development (BDD) User Stories

To ensure engineering has absolute clarity on how the system behaves under varying conditions, the following BDD scenarios must be implemented and tested prior to deployment.

### Story 1: The B2B Guest Coach Acquisition (The Pre-Qualification Flow)
*Feature: The Viral Guest Flywheel*

> **GIVEN** a Guest Coach clicks a "Join Live Coaching Roleplay" Telegram Deep Link sent by an existing CCP Coach  
> **AND** the Daily.co Room is valid and the WebRTC connection is established  
> **WHEN** the 24-minute timer hits 00:00  
> **THEN** the WebRTC connection drops  
> **AND** the app transitions to the `SummaryScreen` React component  
> **AND** a UI modal prompts the three qualification questions (Coach? Audience? Challenge?)
> **AND** if the user selects "Yes" to the final psychological trait
> **THEN** a button labeled "Join the Speaking Audit Law 28 Challenge" is displayed.

### Story 2: Enforcing the 24-Minute Energy Bar
*Feature: Psychological Scarcity*

> **GIVEN** a Coach User has initiated a Roleplay session  
> **AND** the connection has been active for 23 minutes and 40 seconds  
> **WHEN** the backend timer crosses `T = 1420 seconds`  
> **THEN** the Pipecat AI Moderator receives a hard-coded system prompt to execute the `Exit Protocol`  
> **AND** the AI audio overrides human participants to speak the exit phrase  
> **AND** the FastAPI backend fires the Daily.co `DELETE /rooms/{room_name}` endpoint precisely at `T = 1440 seconds`.

### Story 3: Dealing with Participant Disconnection (Edge Case)
*Feature: Roleplay State Management*

> **GIVEN** a 2-Human + AI Roleplay is actively routing video  
> **WHEN** the Guest User's internet connection drops, triggering a WebRTC `iceConnectionState === 'disconnected'` event  
> **THEN** the AI Moderator must pause analysis  
> **AND** the UI must display a "Waiting for Peer Reconnection (30s)" overlay  
> **AND** if the peer does not reconnect within 30 seconds, the room is destroyed  
> **BUT** the Coach User's 24-hour scarcity lockout is **NOT** triggered, allowing them to try again.

### Story 4: Trivianar Sub-Second Button Rendering
*Feature: Native Mini App Broadcasting*

> **GIVEN** a Coach triggers the `QUESTION_1_START` event from the Master Admin Dashboard  
> **AND** 400 users have their Telegram Mini App open  
> **WHEN** the FastAPI server receives the broadcast command  
> **THEN** it pushes a `{"type": "new_question", "payload": {...}}` JSON object down 400 active WebSockets  
> **AND** the React Mini App receives the payload and renders the 4 answer buttons within `< 100ms` of receipt, without ever polling the Telegram Bot API.

### Story 5: Trivianar High-Concurrency Answer Tracking
*Feature: Redis Queue Management*

> **GIVEN** 4,000 users are presented with a Trivia question in the Mini App  
> **WHEN** 4,000 users press an answer button within a 2-second window  
> **THEN** the React frontend emits a `{"type": "submit_answer"}` WebSocket event  
> **AND** the FastAPI server receives it and executes an `LPUSH` payload to Redis  
> **AND** the user UI instantly highlights their choice in `#FFD700` (Yellow) locally  
> **AND** the PostgreSQL database maintains `< 20ms` transaction latency because all 4,000 rights are bulk-processed by the background Celery worker.

### Story 6: Enforcing The "Nervous System" Schema Constancy
*Feature: Database Integrity & Brownfield Compatibility*

> **GIVEN** the New AI Moderator completes its biometric assessment during a Roleplay  
> **WHEN** it is preparing to save the `Interrupt Frequency` and `Mood State Resonance` scores  
> **THEN** it must not create a new standalone table schema  
> **AND** it must append these scores as JSONB variables to the existing `cbcs_interaction_logs` array  
> **AND** it must tag the interaction type as `webRtc_roleplay_module`  
> **SO THAT** the CPSC (Conscious Persuasion Sales Cycle) agents can easily query the data without rewriting the FR-CA11-19 pipelines.
