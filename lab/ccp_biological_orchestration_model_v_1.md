# CCP Biological Orchestration Model

## 1. Purpose

This document consolidates the biological orchestration metaphor that has been present across CCP for a long time but was never formalized cleanly in one place.

The most important lineage documents are:

- `lab/CCP update/Voice_DNA_Framework.md`
- `lab/CCP update/Architecture_Synthesis_Report.md`
- `docs/analysis/brainstorming-session-20260226.md`

This note does not replace the semantic architecture.
It organizes it.

Its job is to answer:

- how all current CCP layers fit together without exploding into conceptual noise
- where old loops remain valid
- where the newer SDA / SFL / variation concepts belong
- how to distinguish runtime orchestration from optimization infrastructure

The governing principle is:

**biology is used as an orchestration model, not as fake neuroscience branding.**

---

## 2. The Main Correction

The older CCP loop:

`primitives -> evals -> score -> real-world outcome -> feedback -> updated evals`

is still valid.

But it only describes the **outer learning loop**.

It does not adequately describe the internal runtime organism.

Likewise, the newer optimization framing:

`primitives -> DSPy + reinforcement language models + activation steering + supervised finetuning -> render / evaluation`

mixes two different things:

- runtime causality
- training / optimization infrastructure

Those must be separated.

The updated CCP model therefore uses three concurrent loops:

1. **Runtime organism loop**
2. **Outer learning loop**
3. **Optimization / model-improvement loop**

---

## 3. The Runtime Organism

The core runtime chain should be understood as:

`DNA -> RNA -> force -> delivery -> variation -> phenotype -> evaluation`

Mapped into CCP, that becomes:

`Voice DNA / Negative Space / SDA / primitive canon / core policies`
`->`
`context packets / trigger packets / invariant field / geometry bind / function stack / depth profile / variation profile`
`->`
`primitive coalition / edge product / activation steering`
`->`
`SFL / rhythmic structure / symbolic compression / strategic ambiguity / repetition with variation`
`->`
`mathematical variation / asymmetry / salience distribution / paradox retention`
`->`
`rendered outputs`
`->`
`semantic, perceptual, and commercial evaluation`

This is the true internal organism.

## 9. The Three CCP Loops

### 9.1 Runtime Organism Loop

This is what happens when the system is producing:

`DNA / truth -> RNA / transcription -> force -> delivery -> variation -> phenotype -> evaluation`

### 9.2 Outer Learning Loop

This is the loop the old CCP model already captured:

`rendered output -> evals -> score -> real-world outcome -> feedback -> updated evals`

This loop remains valid and important.

What changes is that `evals` must now be understood as plural:

- semantic evals
- perceptual evals
- render evals
- commercial outcome evals

### 9.3 Optimization / Model-Improvement Loop

This is where:

- DSPy
- supervised finetuning
- activation steering
- reinforcement language models
- prompt/program revision

belong.

They do not sit directly inside the runtime chain.
They sit above it, learning from:

- runtime traces
- receipts
- score histories
- real-world outcomes
- evaluator disagreements

This loop is:

`runtime traces + scores + outcomes -> optimization stack -> improved modules`

### 9.4 DSPy Exists in Two Real Roles

An important correction is required here.

DSPy should not be treated as only a post-runtime optimization layer.

In CCP, DSPy can and should exist in **two distinct roles**:

#### Runtime DSPy

At runtime, DSPy can act as the typed orchestration substrate that:

- assembles structured reasoning programs
- routes between candidate skills and tools
- enforces typed packet handoffs
- reduces drift compared to raw chat prompting
- keeps the system less chatty and more auditable

In this role, DSPy belongs primarily inside the:

- RNA / transcription layer
- nervous-system / delivery coordination layer

This means DSPy is part of the live organism when:

- function stacks are selected
- content archetype routing is assembled
- skills are executed through typed signatures
- evaluators and downstream modules exchange structured packets

#### Post-Runtime DSPy

DSPy also exists as a post-runtime optimization layer.

In that role, it learns from:

- receipts
- evaluator disagreements
- score drift
- real-world outcomes
- failed or weak runtime traces

to improve:

- signatures
- examples
- typed program composition
- routing logic
- evaluator calibration

So the correct doctrine is:

**DSPy is both a runtime orchestration substrate and an optimization substrate.**

It should never again be described as only “outside runtime.”

### DNA / Truth families emit

### Force families emit

### Protection families emit

- integrity reports
- perceptual influence reports
- hard-negative evaluations
- downgrade / review / block decisions

Receipts should be able to preserve lineage across all these layers rather than only storing primitive weights.

### 10.1 Skill Execution Contracts

Because CCP relies heavily on JIT-created skills, the architecture must distinguish:

- doctrine
- skill strategy
- executable implementation

The older Pi-harness and CCSB work already established the right separation:

- **Skill**
  - the strategic “what” and “why”
  - human-readable doctrine
  - reasoning boundary
- **Schema**
  - the typed contract
  - what inputs, outputs, and guarantees are expected
- **Tool / coded execution unit**
  - the executable “how”
  - Python / TypeScript / DSPy-backed implementation

This means a CCP skill should not be treated as only:

- a long prose prompt
- or a free-form agent instruction

Whenever a skill has repeatable execution logic, it should become at least partially code-backed so it drifts less.

The rule is:

**JIT-created does not mean prose-only.**
**JIT-created should usually mean dynamically assembled, typed, and at least partially executable.**

Examples of executable skill contracts include:

- typed DSPy modules
- Python tool functions with Pydantic schemas
- TypeScript tool functions with Zod schemas
- prompt programs whose strategic layer is separate from execution logic

This is especially important for:

- distillation
- formatting
- profile assembly
- retrieval
- validator handoffs
- render preparation

These should not remain loose prose instructions if they can be codified safely.

## 11. Implications for Specs

This model does not require a fake-neuroscience rewrite of every spec.

It does require that future specs preserve the separation between:

- stable identity truth
- contextual transcription
- force application
- delivery shaping
- variation shaping
- protection and evaluation

The first concrete implications are:

- `FR-ERA3-25` to `28` should remain clearly inside the delivery / variation / protection bands
- future updates to `FR-ERA3-16`, `FR-ERA3-12`, `FR-ERA3-18`, and `FR-ERA3-22` should preserve this layered distinction
- receipts and packets should begin preserving more of the DNA -> RNA -> phenotype lineage
- Pi Harness and skill-execution specs should explicitly distinguish:
  - doctrine-level skills
  - typed schemas
  - executable runtime skill units
  - post-runtime optimization programs

### 11.1 Build-Process Consequence

For building processes, this doctrine should now be treated as executable guidance:

- if a skill is only strategic and judgment-heavy, doctrine may remain prose-first
- if a skill has repeatable mechanics, it should gain typed schema and coded execution
- if a skill routes packets between layers, DSPy is a valid runtime substrate
- if a module improves from outcomes over time, DSPy and steering can also serve as adaptation substrates

This is directly relevant to the Pi Coding Agent Harness.

The harness should not assume:

- giant prompts
- fully improvisational agent behavior
- skills as only markdown

It should assume:

- JIT skill assembly
- typed contracts
- code-backed execution where repeatability matters
- DSPy-mediated runtime orchestration where structured reasoning is required

So yes:

**this is something that matters to the Pi harness build.**
Not because Pi invents the doctrine, but because Pi is where the doctrine becomes operational.
