**Design Proposal 1 — The Four-Zone Immutable Template Architecture** *Grounding: Reber, Schwarz & Winkielman Processing Fluency Theory (2004) \+ Cowan Working Memory Rule of Four (2001) \+ Nielsen & Loranger Aesthetic-Usability Effect (2006)*

The most important design decision is not what goes in the template — it is what stays out. Cowan's research establishes that the true capacity of focused attention is three to five meaningful items. The Rule of Four — the median of this range — is the scientific basis for a non-negotiable architectural constraint: every promotional asset produced by the CPSC contains exactly four active elements. Not five. Not six. Four.

The four zones are fixed in every template regardless of mood state, audience maturity level, or content type. Zone 1 — Hook Zone (top-left): the six-word maximum headline. Zone 2 — Identity Zone (top-right): the coach visual element. Zone 3 — Emotional Core Zone (center diagonal): the atmospheric visual that creates the felt experience of the invitation before any text is read. Zone 4 — Action Zone (bottom-right): a single response mechanism — one line, maximum 12 words, high contrast.

Reber, Schwarz and Winkielman demonstrated physiologically — using facial electromyography — that clean, well-organized visual stimuli trigger micro-activation of the zygomaticus major, the smiling muscle, even without conscious awareness. The viewer does not experience "this is well-designed." They experience "I like this coach." The positive affect generated by processing fluency is misattributed to the message source. The template's structural cleanliness is producing trust before a single word is processed.

The inverse is equally proven and more dangerous: cluttered layouts trigger the corrugator supercilii — the frowning muscle — as a negative affect signal. The viewer experiences "something feels off." They attribute this unease to the coach rather than the design. Poor aesthetic execution is not a minor inconvenience — it is an active trust contamination event that occurs in the 25 milliseconds before any text reaches consciousness.

**Implementation rule:** The Promotional Asset Compiler enforces the four-zone constraint as a hard architectural limit. Any personalization that would introduce a fifth active element — an additional testimonial block, a badge, a decorative element — is rejected by the system. Whitespace is not empty space. It is the mechanism that produces processing fluency. The Canva-equivalent tool locks minimum whitespace ratios in each template zone as parameters that cannot be overridden during personalization.

**Design Proposal 2 — The 25-Millisecond Color Temperature Protocol** *Grounding: Elliot & Maier Color-in-Context Theory (2012) \+ Max Planck Institute Neuro-Temporal Research \+ Labrecque & Milne Brand Personality Color Research (2012)*

Color information reaches the brain's cognitive centers 25 milliseconds faster than shape information. Shape arrives before text — text requiring at least 150 milliseconds for lexical access. This means the color temperature of a promotional flyer is the first message the audience receives, arriving before any other element has been processed. By the time the viewer reads the hook text, the color layer has already established the emotional mode of the entire asset.

The Color-in-Context Theory's most important insight for the CPSC is that color does not have fixed psychological meanings — it has context-dependent meanings. Red does not universally mean urgency. Red in a high-energy challenge invitation context means aliveness and commitment. Red in an achievement context means failure and danger. The meaning is entirely determined by the surrounding emotional context, which in the CPSC's case is the audience's current mood state from DEP-ENG-018.

Four mood-state-calibrated color temperature profiles, each derived from the Kelvin scale research and the Labrecque/Milne brand personality dimensions:

**Escape Mode — Warm Neutral Profile (2700K-3000K):** Soft cream foundations, terracotta or warm amber accents, single warm accent element. Psychological register: comfort, relief, gentle invitation. Physiological mechanism: warm colors reduce cortical arousal in high-stress states, providing the homeostatic comfort that Zillmann's Mood Management Theory identifies as the Escape Mode audience's primary drive. The coach is not asking the exhausted audience to do anything hard — the color temperature signals that before a single word arrives.

**Processing Mode — High Contrast Deep Profile (5000K-6500K):** Dark near-black or deep navy foundation, high contrast light accent (white or pale gold). Psychological register: depth, weight, seriousness. Physiological mechanism: high-contrast cool palettes activate the Labrecque/Milne "Competence" brand personality dimension, signaling that what follows requires and rewards intellectual engagement. A Processing Mode audience is seeking depth — the color temperature signals that this invitation offers it.

**Discovery Mode — Mid-Warmth Energetic Profile (3500K-4500K):** Sage green, warm blue, sunrise amber mid-tones with a bright energetic accent (teal or electric yellow). Psychological register: possibility, curiosity, active engagement. Physiological mechanism: mid-warmth colors balance the approach motivation of warm tones with the trust signals of cool tones — the precise combination that stimulates curiosity without triggering defensive evaluation. Discovery Mode audiences are in open cognitive mode; the color temperature preserves that openness while directing it toward the invitation.

**Status Mode — Premium Dark Profile (Deep charcoal, midnight, forest with gold or platinum accent):** A single high-saturation accent element against a near-black foundation. Psychological register: exclusivity, insider signal, selective invitation. Physiological mechanism: dark premium palettes activate the Labrecque/Milne "Sophistication" brand dimension — the perception that access is selective and therefore valuable. A Status Mode audience is evaluating upward social comparison; the color temperature signals they are being invited into something that not everyone is offered.

**Implementation rule:** The Semiotic Composer Agent queries DEP-ENG-016 (Psychological Routing Brief) for the mood\_state\_primary field and selects the corresponding color temperature profile. The selection is fully deterministic — no creative discretion, no aesthetic judgment. The profile is applied to the template's foundation color, accent color, and typography color weight. The system never reasons about color psychology per piece. The profiles are the pre-computed output of that reasoning. The profiles are applied.

**Design Proposal 3 — The Gaze Vector Architecture: Face Direction as Conversion Mechanism** *Grounding: Frischen, Bayliss & Tipper Meta-Analysis (2007) \+ Tullis, Siegel & Sun Eye-Tracking Research (2009) \+ Langton Joint Attention Mechanism (2000)*

The Frischen meta-analysis of 46 studies established one of the most robust findings in visual attention science: human beings automatically and involuntarily follow the gaze direction of faces in visual material within 50 milliseconds. This gaze cueing effect persists even when participants are explicitly told that the gaze direction is non-predictive — it is stimulus-driven, not goal-driven. The designer can exploit this as a deterministic visual vector: the face captures attention, the gaze transfers that attention to wherever the designer directs it.

The critical finding from Tullis and Breeze's eye-tracking research is the Face Priority Trap — the single most costly error in coaching promotional design. When a coach image looks directly at the camera, heatmaps show intense fixation on the face itself while the headline and call to action are almost entirely ignored. The coach's face has become a dead-end attention event. The social engagement of direct eye contact overrides all commercial intent.

The correction is architecturally simple but neurologically profound. The coach's gaze is directed toward the Hook Zone (top-left) or the Action Zone (bottom-right) depending on the primary conversion objective of the asset. The face captures the audience's attention by evolutionary default. The gaze then transfers that captured attention to the element that drives conversion. The eye physically follows this vector before any conscious decision to read has been made.

Two coach image variants must exist in the asset library for every campaign type. **Awareness-Stage Variant:** gaze directed toward the Hook Zone — for audiences with low TII scores (Entertainment-Social parasocial stage) where establishing what this is about is the primary objective. **Conversion-Stage Variant:** gaze directed toward the Action Zone — for audiences with high TII scores (Intense-Personal stage) where the relationship is established and the objective is directing attention to the response mechanism.

Langton's robustness research resolves the practical concern about using stylized or illustrated coach representations. The joint attention mechanism is equally effective across photographs, illustrations, schematic faces, and vector avatars — provided the geometry of the eyes and head orientation clearly communicate a gaze direction. A brand illustration of the coach with clear gaze direction toward the hook activates the identical neurobiological response as a photograph. This means the coach's brand avatar system can be used in promotional assets without sacrificing the gaze cueing mechanism.

**Implementation rule:** The FR54 Promotional Asset Compiler generates two image variant specifications for every flyer brief — Hook-Directed and Action-Directed. The variant selection is determined by the client's TII score: below 0.5 receives Hook-Directed (establish what this is), above 0.5 receives Action-Directed (direct to the response). The coach image crop and positioning are specified in the brief with explicit gaze direction instruction. Templates lock the Identity Zone size and position to ensure the gaze vector always terminates within the correct target zone — if the face is too far from the hook, the reflexive attention benefit decays before the vector transfer completes.

**Design Proposal 4 — The Six-Word Hook Law: Neurological Non-Negotiable** *Grounding: Paivio Dual Coding Theory (1986) \+ Baddeley Working Memory Model (1974) \+ Nielsen Six-Word Headline Research (150,000 users)*

The Six-Word Headline Law is not a stylistic preference or a copywriting best practice. It is a neurological capacity constraint. Baddeley's Working Memory Model establishes that the phonological loop — the verbal working memory buffer — holds approximately seven items, with more rigorous contemporary research by Cowan establishing the effective focus of attention at three to five meaningful chunks. A headline of five to six words is processed as a single gestalt unit, encoding simultaneously through both Paivio's verbal system and imagery system. A headline of ten or more words forces the brain into sequential chunking — the headline must be processed twice, once to identify the words and again to assemble them into meaning. This dual-pass processing creates a 1.3-second lag in complex stimuli versus simple stimuli, which is the difference between an emotional hook and a discarded piece of paper.

Nielsen's 150,000-user study confirmed the threshold empirically: five to six word headlines are processed 40% faster than headlines exceeding ten words. But the research goes deeper than speed. Headlines within the six-word limit produce immediate intuitive emotional response — the affective centers of the brain register the message before the analytical centers can formulate a resistance response. Headlines exceeding the threshold activate analytical processing first, allowing the viewer's cognitive guard to rise before the emotion has had a chance to land.

The Dual Coding connection is the most architecturally important: when a headline stays within six words, both the verbal logogens and the visual imagens can encode the message simultaneously through referential connections. The words activate the image, the image reinforces the words, and both systems create independent retrieval routes in long-term memory. When a headline exceeds six words, the verbal system's associative processing becomes so dominant that it suppresses the referential connections — the viewer is reading, not experiencing. The emotional architecture of the flyer collapses.

The six-word constraint also has a second function that is not discussed in conventional copywriting advice: it forces the copywriter to distill to the identity-level message. Generic messages that could apply to anyone require more words to compensate for lack of specificity. A six-word identity-targeted hook — written from the Personal Relevance Trigger built from the client's psychological profile — requires exactly six words because it is already at the core. "The confusion was never the problem" is six words. "You have always known what you needed to do" is nine, requires chunking, and arrives analytically rather than emotionally.

**Implementation rule:** The six-word maximum is a hard constraint in the FR54 Promotional Asset Compiler. It is enforced at the generation prompt level — the copy generation prompt specifies "maximum six words, counted before generation, not after." Any hook exceeding six words is rejected and regenerated with a word count constraint reinforced in the instruction. Secondary text has a separate hard constraint of twelve words maximum. Zero body copy on any flyer under any circumstances — the flyer's job is to create a feeling; the voice message's job is to provide context.

**Design Proposal 5 — The Credibility Proximity Principle: Social Proof in the Action Zone** *Grounding: Cialdini Social Proof (1984) \+ Fogg Credibility Research (2002) \+ Metzger, Flanagin & Medders Social Quantity Signal Research (2010)*

Fogg's Credibility Proximity Principle establishes that credibility cues are most effective when positioned in physical proximity to the element that requires credibility — the Action Zone. A social proof count placed at the bottom of a flyer, after the decision point, has minimal conversion effect because the trust signal arrives after the decision moment has passed. The same credibility signal placed adjacent to the call to action transfers its trust directly to the moment of commitment.

Metzger, Flanagin and Medders' 2010 research resolves the testimonial-versus-numbers debate definitively for quick-scan media. In heuristic processing mode — which is the dominant processing state when a viewer first encounters a flyer — social quantity signals (numbers) outperform detailed testimonials by activating the social proof heuristic through peripheral processing. A testimonial requires central processing: the viewer must read the quote, process the narrative, and evaluate the story. A social quantity number — "312 conscious coaches" — activates the herd behavior heuristic instantly through peripheral processing. The viewer concludes legitimacy and popularity without the friction of reading.

The tribal identifier is what elevates the number from generic social proof to identity-aligned social proof. Cialdini's similarity mechanism establishes that social proof carries the most weight when the observer perceives similarity between themselves and the observed group. "312 people" activates weak social proof. "312 conscious coaches" activates strong in-group social proof because it answers the question "people like me?" before it is asked. The tribe identifier is the single word that transforms a statistic into a belonging signal.

The suppression rule from Metzger et al.'s research is equally important and frequently ignored: when participation numbers are low (below ten), social quantity signals produce the opposite effect — activating a negative social proof response ("why has almost no one done this?"). The system must suppress the social proof element entirely when the filtered participant count falls below threshold. Showing ten people joined a previous challenge is worse than showing no social proof at all.

**Implementation rule:** The FR54 Promotional Asset Compiler places a single social proof number in the Action Zone, directly beneath or adjacent to the CTA mechanism. The number is computed as: SELECT COUNT(DISTINCT client\_id) FROM campaign\_performance\_registry WHERE coach\_id \= current\_coach AND tribal\_segment\_match \= TRUE AND conversion\_outcome \= 'enrolled' AND campaign\_type \= matching\_type. This query returns the count of previous participants who match the tribal segment profile of the current campaign's target audience — never the platform total. The tribal identifier is always appended — never a raw number without tribe context. If the filtered count falls below 10, the social proof element is suppressed from the template and the Action Zone layout adjusts to fill the space.

**Design Proposal 6 — The Z-Pattern Flow Architecture: Optical Path Engineering** *Grounding: Nielsen Norman Group Eye Tracking (2006) \+ Djamasbi, Siegel & Tullis Visual Hierarchy (2011) \+ Gutenberg Diagram (1950s, empirically validated)*

The Z-Pattern is the dominant scanning behavior for simplified layouts where a single call to action is the primary objective. The eye travels from top-left to top-right, diagonally to bottom-left, then horizontally to bottom-right. This reading gravity path — validated by the Gutenberg Diagram through decades of print research and confirmed by digital eye-tracking studies — is the architectural spine of every flyer template.

The four-zone template maps directly onto the Z-Pattern's four terminal points. Zone 1 (Hook — top-left) is the Primary Optical Area where the eye begins. Zone 2 (Identity — top-right) is where the first horizontal scan terminates. The diagonal path carries the atmospheric emotional core. Zone 4 (Action — bottom-right) is the Terminal Anchor where the eye naturally arrives and where the conversion decision is made.

Djamasbi et al.'s 2011 study established that visual complexity disrupts the Z-Pattern entirely — when too many competing elements are present, eye movement becomes scattered and unpredictable, making the Z-Pattern path impossible to engineer. This is the scientific confirmation of the four-zone rule from an entirely different research direction. The Z-Pattern and the Rule of Four are not two separate principles — they are two expressions of the same neurological constraint. The template that contains four elements in the correct positions produces Z-Pattern scanning automatically. The template that contains eight elements produces visual chaos and no predictable attention path.

The diagonal path between Zone 2 (Identity) and Zone 4 (Action) is where the gaze vector architecture operates most powerfully. The coach's face in Zone 2, with gaze directed toward Zone 4, creates a gaze vector that runs parallel to the natural Z-Pattern diagonal. The viewer's involuntary gaze following and the natural scanning gravity of the Z-Pattern reinforce each other. The attention flow becomes doubly determined — both neurologically compelled by the gaze cueing mechanism and structurally guided by the Z-Pattern reading gravity.

**Implementation rule:** The Canva-equivalent template system builds Z-Pattern compliance into the template geometry itself. Zone positions are locked — they cannot be moved or resized. Only zone content is customizable. The four-zone layout is not a design recommendation but a fixed architectural specification. A template that allows zones to be repositioned is not a CPSC template — it is a blank canvas that the system will fill incorrectly.

**Design Proposal 7 — The Compression Principle: Whitespace as Conversion Infrastructure** *Grounding: Reber-Schwarz-Winkielman Processing Fluency (2004) \+ Winkielman & Cacioppo EMG Research (2001) \+ Cognitive Load Research (Sweller 1988\)*

Whitespace is not the absence of content. It is the primary mechanism that produces processing fluency — and therefore trust, credibility, and emotional affinity — in promotional assets. Winkielman and Cacioppo's EMG research proved physiologically that easy-to-process stimuli trigger micro-smiles (zygomaticus major activation) and difficult-to-process stimuli trigger micro-frowns (corrugator supercilii activation). Both responses occur below conscious awareness and both are misattributed to the source of the stimulus rather than the design quality of the asset. An asset with generous whitespace produces the micro-smile response. The viewer attributes this to the coach. An asset with crowded elements produces the micro-frown. The viewer attributes this to the coach. This is happening in the first 150 milliseconds — before any text has been read.

The specific function of whitespace in the four-zone template is to create perceptual isolation for each of the four elements. Perceptual isolation means the viewer's working memory encodes each element as a distinct, separate unit rather than as part of a visual cluster that requires parsing. When elements are clustered without whitespace separation, the brain must perform figure-ground segmentation before it can identify individual elements — adding extraneous cognitive load that depletes the resources available for emotional response and decision-making.

Minimum whitespace ratios are not aesthetic guidelines — they are cognitive load budgets. The template must specify minimum pixel margins around each zone that are locked and cannot be reduced during content customization. If a headline is slightly longer than ideal, the solution is to shorten the headline, not to reduce the whitespace margin. The whitespace is never sacrificed for content.

**Implementation rule:** The Canva-equivalent template system locks minimum whitespace ratios as immutable template parameters. Zone margins are specified as minimum values that cannot be reduced. The system validates whitespace compliance before any asset is emitted. If content exceeds the zone boundary, the system returns an error specifying which zone is overflowing and by how many pixels — not a visual override that reduces margins to fit the content.

**On Supabase — Right for Some Things, Wrong for Others**

Supabase is already in your stack and it is the correct choice for relational data and metadata — template registries, avatar registries, render job queues, campaign logs, all the structured queryable data. It is the wrong choice for the actual binary and large-file content.

Three storage layers are needed, not one:

**Cloudflare R2** — for your Fabric.js template JSON files specifically. Template JSONs can be 50-500KB depending on complexity. Storing them as database rows in Supabase creates row size issues and query overhead. Store the JSON file in R2, store the R2 URL in Supabase. The rule: if you need to query it, Supabase. If you need to serve it, UploadThing or R2.

**On Agentic and Modular vs Relational**

You are right to push on this. The distinction matters for how storage is structured.

A relational approach assumes fixed schemas, normalized tables, foreign key relationships, and predictable query patterns. That is correct for your intelligence data — the CBCS scores, the delivery permission gates, the campaign performance registry. These are genuinely relational: a client belongs to a coach, a campaign belongs to a client, a render job belongs to a campaign.

An agentic and modular approach means that skills and agents pass JSON payloads between each other at runtime. The data that flows between agents does not need to be persisted in a relational structure — it exists as a working context object that lives for the duration of a pipeline execution. The only things that get written to Supabase are the inputs, the outputs, and the audit trail. The intermediate states between agents are ephemeral JSON.

For your visual production system this means: the hydrated Fabric.js JSON that the Template Hydration Agent produces does not go into Supabase. It passes directly to the Headless Renderer as a JSON payload in memory. Only the final rendered PNG URL goes to Supabase as part of the campaign asset log. This keeps the database lean and the pipeline fast.

The practical implication: Supabase stores about five things in the visual system. Template registry metadata. Coach avatar registry. Render job status for async monitoring. Campaign asset log. Semiotic combination log for non-repetition tracking. Everything else is either R2 binary storage or ephemeral inter-agent JSON.

**On One Agent or Skill Per Template — Definitely Not**

One agent or skill per template would mean 12 agents for 12 templates, 100 agents for 100 templates. That is not modular architecture — that is explosion of maintenance overhead.

The correct model is one generic skill that takes a template as data, not as code.

The Template Hydration Skill is a single skill that accepts any Fabric.js JSON template and any variable map and produces a hydrated canvas JSON. The template is a parameter, not a hardcoded specification inside the skill. The skill does not know or care whether it is hydrating the Raw Text Assault template or the Film Still template — it applies the same variable injection logic to whatever JSON it receives.

This is the same principle that makes your SKILL.md architecture work: the skill defines the behavior, the inputs define the specifics. A skill that behaves differently based on which template it is hydrating has encoded template knowledge into the skill, which means changing a template requires changing a skill. That breaks modularity.

The only template-specific knowledge that needs to exist anywhere in the system is in the template\_registry metadata in Supabase — the mood\_state\_affinity, visual\_style\_category, maturity\_range, zone\_boundary\_coordinates, and required\_variable\_slots fields that the Template Intelligence Agent reads to make its selection. Once the template is selected, the skill treats it as generic data.

template-loader            → fetches Fabric.js JSON from R2

**What This Changes in the Skill Architecture**

The generic skills remain unchanged — they are the atomic operations. What changes is that each template type now has an explicit **Composition Pipeline** that orchestrates those generic skills in the correct sequence with the correct branching logic.

COMPOSITION PIPELINE LAYER (template-type-specific orchestration)  
├── tweet-visual-pipeline (T1/T2)  
├── branded-meme-pipeline (T3)  
├── cinematic-scene-pipeline (T4)  
├── super-visual-pipeline (T5) — branches on scenario\_count  
├── illustrated-scene-pipeline (T6)  
├── two-panel-comparison-pipeline (T7)  
├── challenge-flyer-pipeline (T8)  
└── webinar-flyer-pipeline (T9)

GENERIC SKILL LAYER (atomic operations, unchanged)  
├── image-acquisition-skill  
│   ├── runninghub-generator  
│   ├── unsplash-searcher  
│   └── asset-retriever (R2/Supabase lookup)  
├── image-compositor (Fabric.js layer assembly)  
├── typography-injector (Fabric.js text placement)  
├── brand-element-injector (coach signature, logo)  
├── template-loader (R2 → Fabric.js JSON)  
├── headless-renderer (Puppeteer → PNG)  
└── visual-qc-validator

VALIDATION GATE LAYER (called by pipelines at defined checkpoints)  
├── six-word-gate  
├── contrast-compliance-checker  
├── zone-overflow-checker  
└── whitespace-ratio-checker

Each pipeline knows its own step sequence and branching conditions. Generic skills do one thing well. The pipeline is the intelligence about composition order — the skill is the execution.

Adding a new template variant (a three-panel comparison, for instance) means writing one new pipeline that reuses existing generic skills. No existing pipeline changes. No existing skill changes. The composition logic is fully isolated in the pipeline layer.

**Layer 2 — Image Processing Modules**

These transform raw acquired images before composition.

MODULE: background-remover  
  Input: image\_url  
  Process: rembg model via RunningHub   
           (dedicated bg-removal workflow, \~3s)  
           OR local rembg if self-hosted  
  Output: transparent\_png\_url  
  When to call: any character/avatar image that was   
                NOT pre-processed during FR0E setup.  
                Pre-processed avatars skip this step entirely.  
  Used by: T3 (character memes), T6 (new character composites)  
  NOTE: Never called during weekly production for coach avatars  
        — they are pre-processed at genesis time

MODULE: image-cropper  
  Input: image\_url, target\_width, target\_height,   
         focal\_point (x,y) or focal\_point\_detection  
  Process: smart crop preserving focal point  
           Uses face detection to auto-set focal\_point   
           when input contains a face  
  Output: cropped\_image\_url  
  Used by: all pipelines that acquire external images

MODULE: color-grader  
  Input: image\_url, grade\_preset\_id  
  Process: applies LUT (Look-Up Table) from preset library  
  Grade presets stored in R2 as .cube files:  
    grade/cinematic-warm     → lifted shadows, warm mids  
    grade/cinematic-cool     → blue shadows, neutral highs  
    grade/high-contrast      → crushed blacks, pulled highs  
    grade/desaturated-matte  → reduced sat, lifted blacks  
    grade/vivid-pop          → boosted sat, contrast punch  
    grade/monochrome         → full desaturate with tone curve  
  Output: color\_graded\_image\_url  
  Used by: T4, T6 (applied to generated or sourced scenes)

MODULE: shadow-overlay-generator  
  Input: image\_url, shadow\_params{opacity, direction,   
         spread, color}  
  Process: generates a soft shadow/vignette layer   
           as transparent PNG overlay  
  Output: shadow\_overlay\_png\_url  
  Purpose: ensures text readability over photographic   
           backgrounds without a hard scrim shape  
  Used by: T4 (bottom text zone legibility)

MODULE: scrim-generator  
  Input: zone\_definition{x,y,width,height},   
         scrim\_params{color, opacity, blur\_edge}  
  Process: generates a gradient fade rectangle   
           as transparent PNG  
  Output: scrim\_png\_url  
  Purpose: semi-transparent overlay behind text zones  
           where image background is complex  
  Used by: T4 (caption bar), T1 variant with photo

**Layer 4 — Typography System**

This is where font definitions live. The typography system is the most precisely specified component because every font decision is a psychological decision.

TYPOGRAPHY REGISTRY  
Stored as: typography\_profiles table in Supabase  
One profile per coach, inherited from brand\_profile

FONT STACK DEFINITION per coach:  
  heading\_font:       primary display typeface  
  subheading\_font:    secondary display or same as heading  
  body\_font:          text content typeface  
  caption\_font:       small secondary text typeface  
  accent\_font:        optional — used for emphasis words only

FONT LOADING:  
  All fonts loaded from Google Fonts CDN at canvas init  
  or self-hosted in R2 as .woff2 files  
  Fabric.js requires explicit font loading before text render:  
  await loadFont(font\_family, font\_url)

MODULE: typography-injector  
  Input: canvas\_json, text\_element{  
    element\_id,         ← matches template slot ID  
    text\_content,  
    font\_role:          heading|subheading|body|caption|accent,  
    size\_preset:        xl|lg|md|sm|xs,  
    weight:             100-900,  
    color\_token:        primary|secondary|accent|inverse|muted,  
    alignment:          left|center|right,  
    max\_width,          ← wrapping boundary in pixels  
    line\_height,  
    letter\_spacing,  
    text\_transform:     none|uppercase|lowercase|capitalize,  
    emphasis\_words\[\],   ← specific words to apply accent\_font/weight  
    x, y,  
    z\_index  
  }  
  Process: resolves font\_role → actual font family from   
           coach typography\_profile  
           resolves size\_preset → pixel value from   
           size\_scale (see below)  
           resolves color\_token → hex from color\_profile  
           applies emphasis to specific words if provided  
           adds Fabric.js IText object to canvas JSON  
  Output: updated canvas JSON

SIZE SCALE (absolute pixel values at 1080px canvas width)  
  xl:   120-180px   → hero headlines, single statement  
  lg:   72-96px     → primary hook text  
  md:   48-60px     → subheadings, panel labels    
  sm:   32-40px     → body statements, captions  
  xs:   20-28px     → secondary labels, attribution,   
                       social proof numbers, handles  
  micro: 14-18px    → fine print, legal, timestamps

These values scale proportionally for other canvas dimensions.  
Stored in typography\_scale table in Supabase.

MODULE: text-emphasis-processor  
  Input: text\_content, emphasis\_rules{  
    bold\_words\[\],    ← specific words to bold  
    color\_words\[\],   ← specific words to colorize   
                        (accent color from profile)  
    italic\_words\[\],  ← italic treatment  
    size\_bump\_words\[\] ← words rendered at next size up  
  }  
  Process: splits text into Fabric.js IText spans  
           applies per-span styling  
           handles line wrapping correctly with mixed styles  
  Output: Fabric.js textbox JSON with mixed formatting  
  Used by: T1 (bold emphasis in tweet body),   
           T2, T4 (bold highlight in headline)  
  NOTE: this is more complex than simple bold — it handles  
        multi-weight text within a single text block,  
        which is what makes Image 2 work   
        ("l'anxiété et la dépression." in bold)

MODULE: text-contrast-enforcer  
  Input: text\_element{color\_hex, x, y, width, height},  
         background\_layer\_url,  
         minimum\_ratio: 4.5 (AA) or 7.0 (AAA)  
  Process: samples background\_layer at text zone   
           average luminance  
           calculates contrast ratio against text color  
           IF below threshold:  
             option 1: switch text to inverse color token  
             option 2: add scrim behind text zone  
             option 3: add text stroke at 1-2px  
           returns correction applied  
  Output: corrected text\_element \+ correction\_log  
  Called after every typography-injector call in pipelines  
  that place text over image backgrounds

**Layer 8 — QC and Validation Modules**

MODULE: zone-overflow-checker  
  Input: rendered\_png\_url, zone\_boundaries\[\]  
  Process: pixel analysis — checks that no non-background  
           pixel exists outside defined zone boundaries  
           for text elements specifically  
  Output: PASS | FAIL{zone\_id, overflow\_pixels}

MODULE: contrast-checker  
  Input: rendered\_png\_url, text\_zones\[{zone, expected\_color}\]  
  Process: samples average luminance in each text zone  
           calculates WCAG contrast ratio  
  Output: PASS | FAIL{zone\_id, ratio, minimum\_required}

MODULE: whitespace-ratio-checker  
  Input: rendered\_png\_url, minimum\_ratio: 0.35  
  Process: calculates percentage of canvas below   
           luminance threshold (empty space)  
  Output: PASS | FAIL{actual\_ratio, minimum\_required}

MODULE: face-presence-validator  
  Input: rendered\_png\_url  
  Process: lightweight face detection (haarcascade or   
           MobileNet face detector)  
           verifies face is present and unobstructed   
           when template requires avatar  
           checks face is in upper portion of identity zone  
           (not cropped, not obscured by text)  
  Output: PASS | FAIL{reason}  
  Used by: T5, T8, T9 (avatar-present templates)

MODULE: brand-consistency-checker  
  Input: rendered\_png\_url, brand\_profile{  
    primary\_color, secondary\_color, accent\_color  
  }  
  Process: dominant color extraction from rendered image  
           checks that at least one brand color appears  
           within 15% hue tolerance  
  Output: PASS | WARNING{dominant\_colors\_found}  
  WARNING does not block — alerts operator for review

**Layer 9 — Components Worth Adding**

These do not exist yet but would materially improve the system.

MODULE: caption-auto-generator (HIGH VALUE)  
  Input: script\_text, max\_words: 12, style: quote|stat|question  
  Process: extracts highest-resonance sentence from script  
           via semantic importance scoring  
           returns the single sentence most likely to stop scroll  
  Output: caption\_text  
  Reason to add: currently caption text would be manually

                 content directly.

  Input: color\_profile, stage\_set\_id  
  Process: checks that stage set's dominant colors do not   
           clash with brand color profile  
           uses HSL distance calculation  
           e.g. prevents a warm orange brand accent on a   
           warm orange stage set (no separation)  
  Output: PASS | FAIL{recommendation: alternative\_stage\_id}  
  Reason to add: prevents visually muddy compositions where   
                 avatar/text and background merge tonally

MODULE: visual-non-repetition-checker (ALREADY SPECIFIED)  
  Input: coach\_id, semiotic\_combination\_hash, lookback\_weeks: 8  
  Process: queries semiotic\_combination\_log table  
  Output: PASS (combination not used) | FAIL (used N weeks ago)  
  This module enforces the 8-week rotation rule

MODULE: aspect-ratio-adapter (MEDIUM VALUE)  
  Input: canvas\_json (1080x1080), target\_format: portrait|square  
  Process: intelligently adapts composition for alternate   
           aspect ratio — does not simply crop  
           repositions elements to work in new proportions  
           expands vertical canvas with additional padding  
  Output: adapted canvas JSON at new dimensions  
  Reason to add: some coaches need both square and portrait   
                 from the same content piece without   
                 running the full pipeline twice

MODULE: a11y-text-size-enforcer (LOW PRIORITY, HIGH PRINCIPLE)  
  Input: typography\_element{size\_px, canvas\_width}  
  Process: ensures minimum effective text size of 16px   
           equivalent at standard mobile display size  
           (1080px canvas displayed at \~390px width \= 0.36 scale)  
           so minimum canvas size \= 16 / 0.36 \= 44px  
  Output: PASS | correction{recommended\_size}  
  Reason to add: ensures legibility on small phone screens  
                 where 90% of your audience views content

MODULE: emoji-preprocessor (REQUIRED FOR T1/T2)  
  Input: text\_content\_with\_emoji  
  Process: detects emoji characters  
           converts each emoji to its image representation  
           (using Twemoji or Apple emoji CDN)  
           returns text segments \+ inline image objects  
  Output: mixed content array for text-emphasis-processor  
  Reason to add: Fabric.js does not render emoji glyphs   
                 reliably cross-platform. This is required   
                 for T1/T2 tweet visuals to look correct.

MODULE: image-semantic-tagger (FUTURE VALUE)  
  Input: image\_url (newly acquired or generated)  
  Process: vision model analysis of image content  
           tags: dominant\_colors\[\], mood\_register,   
                 has\_face, face\_count, scene\_type,   
                 negative\_space\_zones\[\]  
  Output: image\_metadata tags written to asset record  
  Reason to add: allows stage\_set query to become semantic  
                 rather than just metadata-based. "Find a   
                 stage that feels like early morning quiet"   
                 becomes possible.

**The Swap Intelligence System**

The `swap_compatible_with` field on every node is the mechanism that makes intelligent swapping possible. It declares which modules and component types can replace this node without breaking the composition.

Three swap modes:

**Mode 1 — Direct Component Swap** Replace one node with a different asset of the same type. Same position, same layer, same role. Different visual content.

Swap operation:  
  asset\_id: AST-2026-031509-T4-TRES-001  
  node\_id: NODE-L0 (background)  
  swap\_type: direct  
  new\_component: STG-concrete-dark-1080  
    
System:  
  1\. Load original composition graph  
  2\. Replace L0 node with new\_component  
  3\. Re-run contrast-checker (background changed, text readability may shift)  
  4\. Re-run color-harmony-validator  
  5\. Re-render  
  6\. Save as AST-2026-031509-T4-TRES-001-v2  
     parent\_asset\_id: AST-2026-031509-T4-TRES-001-v1

**Mode 2 — Parameter Swap** Keep the same component type, change the parameters. Headline text changes but font and position stay identical.

Swap operation:  
  asset\_id: AST-2026-031509-T4-TRES-001  
  node\_id: NODE-L3 (headline)  
  swap\_type: parameter  
  param\_overrides:  
    text\_content: "80% DES JOUEURS RETRAITÉS SOUFFRENT DE DÉPRESSION."  
    emphasis\_words: \["80%", "DÉPRESSION"\]  
      
System:  
  1\. Load original composition graph  
  2\. Update L3 node parameters only  
  3\. Re-run six-word-gate (text changed)  
  4\. Re-run contrast-checker at headline zone  
  5\. Re-render  
  6\. Save as v2

**Mode 3 — Structural Clone with Swaps** Clone the entire composition graph and apply multiple swaps simultaneously. This is variant production — same structure, different content.

Clone operation:  
  source\_asset\_id: AST-2026-031509-T4-TRES-001  
  swaps: \[  
    { node: L0, new\_component: STG-golden-hour-desk-1080 },  
    { node: L3, params: { text\_content: "NEW HEADLINE" } },  
    { node: L4, params: { text\_content: "New caption text" } }  
  \]  
    
System:  
  1\. Deep copy composition graph  
  2\. Apply all swaps to copy  
  3\. Run full validation pipeline  
  4\. Render  
  5\. Save as AST-2026-031509-T4-TRES-002  
     cloned\_from\_asset\_id: AST-2026-031509-T4-TRES-001

**The Swap Intelligence Queries**

\-- What performed best for T4 templates in the last 30 days?  
SELECT   
  composition\_graph-\>'layer\_0\_background'-\>\>'processed\_url' as background,  
  composition\_graph-\>'layer\_3\_headline'-\>\>'text\_content' as headline,  
  performance\_data-\>'engagement\_metrics'-\>\>'save\_rate' as save\_rate  
FROM asset\_history  
WHERE coach\_id \= $coach\_id  
  AND template\_id LIKE 'T4%'  
  AND created\_at \> NOW() \- INTERVAL '30 days'  
ORDER BY (performance\_data-\>'engagement\_metrics'-\>\>'save\_rate')::float DESC  
LIMIT 10;

\-- Which backgrounds have been used in the last 8 weeks?  
\-- (Non-repetition enforcement)  
SELECT DISTINCT   
  composition\_graph-\>'layer\_0\_background'-\>\>'component\_type',  
  composition\_graph-\>'layer\_0\_background'-\>\>'processed\_url'  
FROM asset\_history  
WHERE coach\_id \= $coach\_id  
  AND created\_at \> NOW() \- INTERVAL '8 weeks';

\-- Full lineage of an asset including all versions and clones  
WITH RECURSIVE asset\_tree AS (  
  SELECT asset\_id, version, parent\_asset\_id, cloned\_from\_id, created\_at  
  FROM asset\_history  
  WHERE asset\_id \= $root\_asset\_id AND version \= 1  
    
  UNION ALL  
    
  SELECT ah.asset\_id, ah.version, ah.parent\_asset\_id, ah.cloned\_from\_id, ah.created\_at  
  FROM asset\_history ah  
  JOIN asset\_tree at ON   
    ah.parent\_asset\_id \= at.asset\_id OR   
    ah.cloned\_from\_id \= at.asset\_id  
)  
SELECT \* FROM asset\_tree ORDER BY created\_at;

\-- Find all assets with the same semiotic combination  
\-- (detect repetition before producing a new asset)  
SELECT asset\_id, version, created\_at, output\_url  
FROM asset\_history  
WHERE coach\_id \= $coach\_id  
  AND semiotic\_hash \= $proposed\_hash  
  AND created\_at \> NOW() \- INTERVAL '8 weeks';

\-- Which components across the entire asset library  
\-- have the highest average save rate when used as background?  
SELECT   
  composition\_graph-\>'layer\_0\_background'-\>\>'processed\_url' as component\_url,  
  COUNT(\*) as usage\_count,  
  AVG((performance\_data-\>'engagement\_metrics'-\>\>'save\_rate')::float) as avg\_save\_rate  
FROM asset\_history  
WHERE coach\_id \= $coach\_id  
  AND performance\_data-\>'engagement\_metrics'-\>\>'save\_rate' IS NOT NULL  
GROUP BY composition\_graph-\>'layer\_0\_background'-\>\>'processed\_url'  
HAVING COUNT(\*) \>= 3  
ORDER BY avg\_save\_rate DESC;

That last query is the intelligence loop. After enough assets have performance data attached, the system can answer: "For this coach, which background component produces the highest save rate?" The Variable Resolution Agent queries this before selecting a stage set — it is not just picking from the library, it is picking the historically best-performing option for this coach's specific audience.

**The Core Insight**

A Fabric.js template JSON is already a structured document describing layers, their types, their positions, and their element IDs. An agent that reads this JSON can infer:

* How many layers exist and in what z-index order  
* Whether each layer is an image, text, shape, or group  
* Which layers have variable slot IDs (meaning they accept dynamic content) versus structural IDs (meaning they are immutable)  
* What acquisition method each image slot needs based on its ID naming convention  
* What validation gates apply based on layer type and position  
* Whether multi-panel structure exists (detectable from grouped zones)  
* Whether text zones overlap image zones (requiring contrast checking)

From these inferences it can generate approximately 70-80% of the pipeline automatically. The remaining 20-30% requires human decisions that cannot be inferred from visual structure alone — which RunningHub workflow to use for generation, what the semiotic hash formula should be, what the swap\_compatible\_with declarations should be.

**The Template Analysis Agent**

AGENT: Template Analysis Agent  
TRIGGER: /ccf-template register \[template\_id\]  
INPUT: Fabric.js JSON exported from Canva clone editor  
OUTPUT:   
  \- Draft composition pipeline  
  \- Component manifest (every module required)  
  \- Variable slot map  
  \- Inferred QC gate sequence  
  \- Human decision request list (the 20% it cannot infer)

The agent runs four analysis passes over the Fabric.js JSON.

**Pass 1 — Layer Inventory**

Reads every object in the Fabric.js canvas JSON. For each object extracts: element\_id, type (image/text/rect/group), z\_index, position (x,y,width,height), locked status, opacity, any existing style parameters.

Classifies each object as one of three categories:

STRUCTURAL — element\_id does NOT match variable slot naming convention  
  These are immutable. Border frames, dividers, brand marks   
  with fixed content, background shapes.  
  Pipeline step generated: none (baked into template JSON)

VARIABLE\_SLOT — element\_id matches naming convention  
  These accept dynamic injection.  
  Naming convention enforced:  
    slot\_bg\_\*        → image acquisition \+ layer-compositor  
    slot\_avatar\_\*    → asset-retriever/avatar \+ layer-compositor    
    slot\_character\_\* → asset-retriever/character \+ layer-compositor  
    slot\_stage\_\*     → asset-retriever/stage-set \+ layer-compositor  
    slot\_text\_\*      → typography-injector  
    slot\_icon\_\*      → icon-injector  
    slot\_coach\_\*     → tweet-chrome-renderer or profile element  
    slot\_social\_\*    → social-proof-resolver \+ typography-injector  
    slot\_cta\_\*       → cta-generator \+ typography-injector

INFERRED\_STRUCTURAL — element\_id is generic but type analysis   
  reveals it should be structural (e.g. a rectangle with brand   
  color that is clearly a frame, not a variable slot)  
  Agent flags these for human confirmation

**Pass 2 — Composition Sequence Inference**

Orders pipeline steps by z\_index of variable slots. Lower z\_index slots are acquired and composited first. This correctly determines that backgrounds are acquired before avatars, avatars before text, text before watermarks.

Also detects multi-panel structure: if the template contains two or more image zones with similar dimensions arranged in a grid pattern, it infers panel\_count and generates a panel-divider step.

**Pass 3 — QC Gate Inference**

Automatically determines which validation gates must run based on composition analysis:

IF any slot\_text\_\* zone overlaps or sits adjacent to slot\_bg\_\* or slot\_stage\_\*:  
  → add contrast-checker to QC sequence  
  → add text-contrast-enforcer to that typography-injector step

IF any slot\_avatar\_\* or slot\_coach\_\* exists:  
  → add face-presence-validator to QC sequence

IF template\_type is T8 or T9 (detected from slot naming patterns):  
  → add six-word-gate before slot\_text\_hook injection  
  → add central-route-trigger-validator  
  → add whitespace-ratio-checker

IF multi-panel detected:  
  → add zone-overflow-checker per panel

ALWAYS:  
  → add visual-non-repetition-checker  
  → add brand-consistency-checker

**The Formal Template Registration Protocol**

This is the official process. Every template that enters the system must pass through all five stages. No template goes into production without a completed registration.

STAGE 1 — DESIGN (Human)  
  Tool: Canva Clone editor

  1\. Naming Convention Enforcement

     shown in orange as a warning, not a block.  
    
  2\. Lock Declaration  
     Structural elements must be explicitly locked using   
     the editor's lock function. The export includes a   
     locked\_elements\[\] array listing all locked element IDs.  
    
  3\. Zone Boundary Export  
     The editor fork adds a "Zone Boundaries" tool —   
     the designer draws invisible rectangles over each   
     functional zone and labels them (hook\_zone,   
     identity\_zone, action\_zone, etc). These export   
     as zone\_boundaries\[\] in the template JSON.  
     This is the data the QC modules use for overflow checking.  
    
  4\. Typography Pre-declaration  
     Text slot elements should have their font\_role   
     set in the element's custom properties panel   
     (heading/subheading/body/caption/accent).  
     If not set, the agent infers from size but flags for   
     human confirmation.

**2 — The RunningHub API Route**

// src/app/api/runninghub/generate/route.ts

export async function POST(req: Request) {  
  const { workflowId, inputs, targetSlot, canvasId } \= await req.json()  
    
  // Create RunningHub task  
  const taskResponse \= await fetch(  
    "https://api.runninghub.ai/task/create",  
    {  
      method: "POST",  
      headers: {  
        "Content-Type": "application/json",  
        "Authorization": \`Bearer ${process.env.RUNNINGHUB\_API\_KEY}\`  
      },  
      body: JSON.stringify({ workflowId, inputs })  
    }  
  )  
    
  const { taskId } \= await taskResponse.json()  
    
  // Poll for completion  
  const imageUrl \= await pollForCompletion(taskId)  
    
  // Upload to R2 immediately  
  // (ensures we own the URL, not dependent on RunningHub CDN)  
  const r2Url \= await uploadToR2(imageUrl, {  
    key: \`generated/${canvasId}/${taskId}.png\`,  
    metadata: { workflowId, prompt: inputs.positive\_prompt }  
  })  
    
  // Log generation to asset\_history  
  const generationId \= await logGeneration({  
    workflowId,  
    prompt: inputs.positive\_prompt,  
    rawUrl: imageUrl,  
    r2Url,  
    targetSlot,  
    canvasId  
  })  
    
  return Response.json({ imageUrl: r2Url, generationId })  
}

async function pollForCompletion(taskId: string): Promise\<string\> {  
  const maxAttempts \= 60 // 120 seconds at 2s intervals  
    
  for (let i \= 0; i \< maxAttempts; i++) {  
    await new Promise(r \=\> setTimeout(r, 2000))  
      
    const status \= await fetch(  
      \`https://api.runninghub.ai/task/status/${taskId}\`,  
      { headers: { "Authorization": \`Bearer ${process.env.RUNNINGHUB\_API\_KEY}\` } }  
    )  
      
    const { status: taskStatus, outputUrl } \= await status.json()  
      
    if (taskStatus \=== "completed") return outputUrl  
    if (taskStatus \=== "failed") throw new Error(\`RunningHub task ${taskId} failed\`)  
  }  
    
  throw new Error(\`RunningHub task ${taskId} timed out\`)  
}

  Input: prompt \+ workflow\_id \+ params  
  Output: image PNG stored in R2 with all generation   
          params saved on the asset record  
  When: happens FIRST, can happen ahead of time,  
        can be triggered manually or by agent

OPERATION 2 — COMPOSITION (fast, \<3 seconds)  
  Input: template JSON \+ resolved variable map  
         (image slots already have R2 URLs)  
  Output: final rendered PNG  
  When: happens AFTER generation is complete,  
        never triggers generation itself

Generation and composition are separate skills. They never call each other. The composition skill assumes all image URLs are already resolved when it runs. It never waits for RunningHub.

---

**Why This Separation Matters**

If you need to change the headline text — you run composition only. No RunningHub call. Sub-3 seconds.

If you need a new background — you run generation only, store the new URL, then run composition with the updated variable map.

If you want 10 carousel variants — you run generation once per unique image needed, then run composition 10 times with different text variables against the same images. No redundant generation.

If a generated image from 3 days ago is still good — composition reuses the stored R2 URL directly. RunningHub is never called again for that asset.

**The Two Skills**

SKILL: runninghub-generate  
  Input:  
    workflow\_id: string  
    prompt: string  
    params: { seed, steps, cfg, width, height,   
              negative\_prompt, ...workflow\_specific }  
  Process:  
    POST to RunningHub API  
    Poll until complete  
    Upload result to R2  
    Write asset record to Supabase:  
      { asset\_id, workflow\_id, prompt, params,   
        r2\_url, generated\_at }  
  Output:  
    { asset\_id, r2\_url }  
    
  This skill knows nothing about templates.  
  It only generates and stores.

SKILL: template-compose  
  Input:  
    template\_id: string (loads JSON from R2)  
    variables: {  
      "SLOT-image-scene": "r2://...already-generated.png",  
      "SLOT-text-headline": "LE CENTRE DE FORMATION...",  
      "SLOT-text-caption": "\\"Pas d'explication...\\""  
    }  
  Process:  
    Load template JSON from R2  
    For each variable:  
      Find matching SLOT- element in JSON  
      Update src or text  
    POST modified JSON to Canva Clone /api/render  
    Receive PNG  
    Store in R2  
    Write to asset\_history with full composition graph  
  Output:  
    { asset\_id, r2\_url }  
    
  This skill knows nothing about RunningHub.  
  It only composes and renders.

**How Generation Params Travel**

The generation params live on the **asset record in Supabase**, not on the template. When composition runs, it writes the asset\_id of every generated image into the composition graph. That reference is the link back to the generation params.

asset\_record (Supabase)  
  asset\_id: "GEN-4829103-031509"  
  workflow\_id: "cinematic-scene-v1"  
  prompt: "dramatic football pitch..."  
  params: { seed: 4829103, steps: 20, cfg: 7.5 }  
  r2\_url: "r2://generated/GEN-4829103.png"

composition\_graph (asset\_history)  
  layer\_0:  
    asset\_id: "GEN-4829103-031509"  ← reference to generation  
    r2\_url: "r2://generated/GEN-4829103.png"

When someone wants to regenerate — they look up the asset\_id, read the generation params from the asset record, call runninghub-generate with those params, get a new asset\_id and URL, and pass the new URL into template-compose.

The template never changes. The image asset is what changes. The two are decoupled.
