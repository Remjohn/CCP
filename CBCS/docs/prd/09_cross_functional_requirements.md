# **9\. Cross-Functional Requirements**

## **9.1 Data Strategy: From Unstructured Stream to Psychological Graph**

The transition to a conversational, agent-orchestrated interface fundamentally changes the nature of our data strategy. We are moving from a paradigm of discrete, synchronous inputs (clicks, form submissions, toggle switches) to a paradigm of continuous, unstructured, asynchronous "streams" of voice and text.

In a traditional application, data integrity is maintained by database constraints. In the **Conscious Behavioral Change System**, data integrity is maintained by **Semantic Consistency**. To make the unstructured data actionable for the **Neuro-Persuasion Engine**, the system must enforce a rigorous transformation pipeline that converts raw audio (Soul Data) into a structured **Psychological Graph** (Context Premise).

### **9.1.1 The Entity Extraction Pipeline (Soul Data Harvesting)**

The system must not simply act as a digital tape recorder storing raw transcripts. It must function as an active psychoanalyst. **Aria (The Synthesizer)** is the guardian of this pipeline. She utilizes **Pydantic AI** to enforce a strict schema extraction process on every incoming message.

The Extraction Logic:

Every time Groq returns a raw text transcript from a user Voice Note, it is passed through a dedicated extraction agent. This agent does not summarize; it categorizes. It maps the chaotic, emotional language of the user to the 12 specific dimensions of the Context Premise defined in the Intelligence Library.

* **Enemy Identification:** The extractor must parse the text for external blockers. If a user says, "My boss is riding me hard today," Aria must identify "My Boss" as an entity and map it as an Enemy node in **Neo4j**. This allows **The Assembler** to later query this specific node when selecting the "Throw Rocks at Enemies" persuasion angle.  
* **Fear Mapping:** It must detect expressions of anxiety or hesitation. "I'm afraid I'll look stupid if I try this" is mapped as a Fear node labeled "Social Judgment." This enables the "Allay Fears" script logic to reference the specific fear, rather than offering generic reassurance.  
* **Hidden Belief Detection:** It must detect limiting scripts that the user treats as facts. "I'm just not a math person" or "I've always been heavy" are extracted as Hidden\_Belief nodes. These become targets for the "Challenger" layer to dismantle via Reverse Psychology.  
* **Success Marker Tracking:** It must identify what the user considers proof of progress. If they say, "I finally slept through the night," this is extracted as a Success\_Marker.

TTT State Tagging:

Every interaction must be tagged with a Temperament, Temperature, and Tone (TTT) level ranging from 01 to 09\. This is not merely metadata; it is a state trigger for the LangGraph workflow. If Aria detects TTT-02 (Defeated) for three consecutive days, the system must trigger a specific "Recovery Protocol" state transition, overriding the standard curriculum with restorative content.

Constraint Detection:

Any mention of physical limitations or injuries must be treated with the highest priority. Phrases like "my knee hurts," "I had surgery," or "my back is acting up" must be extracted and stored in a physical\_constraints JSONB column in Supabase and as a Constraint node in Neo4j. This acts as a hard safety filter; if a constraint exists, Atlas (The Program Architect) is structurally forbidden from prescribing high-impact rituals from the Pantry.

### **9.1.2 Data Lifecycle & Storage Tiering**

Voice assets are high-bandwidth, high-storage, and highly sensitive. We cannot treat them like text logs. The system must implement an automated lifecycle policy to manage costs and privacy while preserving the "Memory" of the transformation.

**The "Hot/Cold" Storage Policy:**

* **Hot Storage (0-30 Days):** Raw audio files are kept in high-availability **Supabase Storage** buckets. These must be instantly accessible via the Coach Dashboard for **"Operator Mode"** interventions. If a Coach needs to "Intercept" a client, they need to hear the raw voice note to understand the nuance.  
* **Cold Storage (31-90 Days):** Files are moved to cheaper archival storage. They remain retrievable but with higher latency.  
* **The Purge (\>90 Days):** Raw biometric audio files are permanently deleted to minimize liability and storage bloat. However, the **text transcripts** and the **semantic embeddings** (stored in **pgvector**) must be retained indefinitely. This ensures that the Agent's long-term memory of the client's journey remains intact even after the raw audio is gone.

The Consent State Machine:

For gamification assets like "Voice Testimonials," the system must maintain a strict state of "Content Consent." A voice note flagged as a testimonial is PRIVATE by default. Only upon receiving an explicit "YES" to the consent prompt generated by the protocol does the flag switch to PUBLIC. This enables the asset to appear on the Live Leaderboard or be used in marketing funnels. This state must be auditable and reversible.

## **9.2 Integration Resilience & Idempotency**

The **"Invisible App"** relies on a fragile web of third-party dependencies: Telegram for the interface, Stripe for economics, OpenAI/MiniMax for reasoning, Groq for hearing, and Runpod for speaking. If one fails, the "illusion of presence" breaks. Cross-functional requirements ensure resilience when these external systems fluctuate.

### **9.2.1 Telegram Webhook Governance**

Strict Idempotency:

The FastAPI webhook handler must implement strict idempotency keys based on the wamid (Telegram Message ID). Telegram's API is aggressive; during network congestion or timeout events, it will frequently send the same webhook payload twice. If the system processes the same message twice, it might trigger the Neuro-Persuasion Engine twice, resulting in the user receiving two different audio replies to the same statement. This breaks the "human" illusion immediately. The system must cache processed IDs in Redis for 24 hours. If a duplicate ID arrives, the system must return 200 OK immediately without re-triggering the costly AI pipeline.

Rate Limit Governance:

The outbound message queue must be "Rate-Aware." It must track the rolling window of messages sent to specific users. If the queue detects that it is approaching the Telegram API limits (30 messages per second globally, or 1 message per second per user), it must throttle non-essential traffic. For example, "Streak Flame" images or "Victory Cards" can be delayed, but the critical "Morning Hook" delivery must be prioritized.

### **9.2.2 Stripe Connect & Provisioning**

The "Payment-First" Gate:

The integration between Stripe and Supabase must be atomic. A user account cannot be provisioned until the payment\_intent.succeeded webhook is cryptographically verified. This prevents "Ghost Users" from entering the graph database and consuming expensive GPU resources without paying.

Metadata Pass-Through:

The Stripe integration must support deep metadata pass-through. When a user buys a specific "5-Day Challenge" via a payment link, the webhook must carry the program\_id and coach\_id. The system must use this to automatically enroll the user in the correct Neo4j program track and trigger the specific Onboarding Script for that program immediately. Manual provisioning by the coach is prohibited; the system must be zero-touch from purchase to first interaction.

### **9.2.3 Media Integrity (The Lego Blocks)**

Privacy Verification:

The system must utilize the YouTube Data API to validate the privacy status of every video link added to the Component Pantry.

* **The "Unlisted" Rule:** If a Coach tries to use a "Private" video (which clients cannot see) or a "Deleted" video, the system must throw a validation error during the upload phase. It must not wait for a client to report a broken link during a morning ritual, as this destroys the momentum of the **"Vision Implant"** and breaks the flow state.

## **9.3 Operational Requirements**

These requirements define how we keep the "heartbeat" of the system running 24/7 without crashing under load, specifically managing the "Thundering Herd" problem of morning routines.

### **9.3.1 The "8:00 AM Thundering Herd" Management**

Sending 5,000 high-fidelity voice notes at exactly 08:00 AM would crash our **Runpod** GPU cluster and trigger Telegram spam filters immediately. The system must treat time as a flexible variable, not a fixed constant.

Jitter Logic:

The Cron job responsible for the Morning Hook must implement "Jitter" logic. It must distribute the send times for a specific timezone over a 15-minute window (e.g., between 08:00:00 and 08:15:00 AM).

Priority Queuing:

The queue must be intelligent. It must prioritize "High Risk" clients (those tagged with TTT-02 or recent failures in Neo4j) to ensure they receive their priming message first. Stable clients ("Flow State") can receive their messages later in the window.

Dead Letter Queues:

If a message fails to send (e.g., Telegram API 500 error), it must not be lost. It must be moved to a "Retry Queue" with exponential backoff. If it fails permanently (3 attempts), it must be logged to a "Delivery Failure" list on the Coach Dashboard so the coach can manually follow up via Operator Mode.

### **9.3.2 GPU Cold Start & Latency Monitoring**

Latency Alerts:

We must monitor the specific execution time of the IndexTTS-2 (Voice Synthesis) service via Langfuse. If the average latency exceeds 15 seconds for a period of 5 minutes, a "Degraded Performance" alert must be sent to the engineering team.

Keep-Warm Validation:

The system must log the success/failure of the 5-minute "Keep-Warm" pings sent to Runpod. If a ping fails, the system must immediately attempt to restart the container to ensure it is ready for the morning rush. This is critical to maintaining the "Thinking Gap" illusion; if the gap stretches to 45 seconds, the user disengages.

### **9.3.3 Support Escalation Protocol (The "Human Hand-off")**

Frustration Detection:

If the Pydantic AI sentiment analyzer detects frustration keywords (e.g., "stupid bot," "stop messaging me," "let me talk to a human"), LangGraph must immediately execute a "Soft Stop."

Action:

It stops the auto-responder loop and sends a high-priority "Intervention Request" to the Coach's Telegram. The system is structurally forbidden from arguing with a frustrated user. It must yield to a human immediately to preserve the relationship capital. This "Safety Valve" is a critical operational requirement for high-ticket coaching.

## **9.4 User/Agent Responsibilities Matrix**

To avoid confusion and "Automation Bias" (where the Coach trusts the AI too much), we must explicitly define the division of labor within the architecture. The system is designed for **Human-in-the-Loop** AI, not fully autonomous AI.

* **Program Design (Coach):** The Coach defines the "Lego Blocks" (Rituals), records the videos, and tags them in the Pantry. The AI cannot invent content; it can only assemble it.  
* **Identity Engineering (AI Agent):** The AI executes the daily **Neuro-Persuasion** loop. It selects the bias, generates the script, and synthesizes the voice. This is fully automated.  
* **Crisis Detection (AI Agent):** The AI scans for patterns of failure or distress (TTT-02). It does not solve the crisis; it flags it via the **Red Flag Feed**.  
* **Crisis Resolution (Coach):** The Coach uses **Operator Mode** to intervene personally when a client is injured or at risk of churn. The AI steps back during this phase.  
* **Gamification Voting (Clients):** Clients peer-vote on testimonials. The Coach facilitates the ceremony, but the community determines the winner.

## **9.5 Documentation & Ubiquitous Language**

In an **"Invisible App"** driven by psychology, ambiguity is dangerous. A developer might interpret "Compassionate Response" differently than a psychologist. Therefore, strict adherence to a shared vocabulary is a system integrity requirement. **Domain-Driven Design (DDD)** principles are applied to ensure the code speaks the language of the business and the psychology.

### **9.5.1 Code-Domain Parity**

Variable names in the codebase must match the Domain Terms defined in the **Intelligence Library** exactly.

* **Violation:** user.mood\_score  
* **Correction:** daily\_log.morning\_ttt\_state  
* **Violation:** app.send\_notification  
* **Correction:** telegram.send\_vision\_implant

Rationale:

If a developer thinks in terms of "Notifications," they will optimize for delivery speed and throughput. If they think in terms of "Vision Implants," they will optimize for the 3-second psychological delay and the persuasive framing. Language shapes architecture.

### **9.5.2 The "Failure" Redefinition**

In all documentation, code comments, and internal communication, a missed ritual is never referred to as a "Failure" in the context of the user's character. It is referred to as a **"Data Point"** or **"Dissonance Signal."**

Application:

This semantic shift must be reflected in the code logic. We do not flag streak\_broken \= true immediately upon a miss; we flag status \= pending\_accountability. This ensures the LangGraph logic allows for the "Compassionate Retrieval" flow to occur before a streak is visually broken on the dashboard. The code must assume that a "Miss" is simply "Context for Tomorrow" until proven otherwise.

### **9.5.3 Architectural Decision Records (ADRs)**

Given the complexity of the **Agent-Orchestrated** model, technical decisions often have cascading effects on latency and cost. All major architectural decisions must be recorded in an **Architecture Decision Record (ADR)** repository.

* **Example:**  
  * *Context:* "08:00 AM latency is 45 seconds due to GPU queuing."  
  * *Decision:* "Pre-generate audio files at 07:45 AM and store in Supabase."  
  * *Consequence:* "Personalization is locked 15 minutes prior; real-time weather data must be fetched at 07:45, not 08:00."

## **9.6 Stakeholder Alignment & Quality Control**

The "Black Box" nature of Generative AI creates anxiety for stakeholders. They cannot "see" what the AI is saying to every client every day. We must establish specific protocols to manage this anxiety and validate the quality of the **Neuro-Persuasion**.

### **9.6.1 The "Bot Council" Review**

A weekly 45-minute review session is mandated between the Product Owner, Lead Developer, and the Primary Coach.

* **Activity:** The team reviews a random sample of 20 anonymized transcripts from the previous week via the Dashboard. They listen to the generated audio and read the user's reply.  
* **Goal:** To calibrate the "Temperature" of the AI.  
* **Scenario:** "The AI used the 'Challenger' (Angle 2\) persuasion on a client who was grieving. This caused recoil."  
* **Action:** Create a ticket to adjust the **Neo4j** constraint logic or the **Pydantic AI** sentiment validator thresholds to prevent TTT-08 usage when negative sentiment is high. This ritual restores the Coach's sense of control over the automated system.

### **9.6.2 The "Silver Surfer" Proxy**

The Product Owner is designated as the "Guardian of the Demographic."

* **Veto Power:** The PO has absolute veto power over any feature that requires "Learning." If a feature requires the user to learn a gesture, memorize a command, or understand a new UI paradigm, the PO must reject it.  
* **Validation:** Every new feature must be tested against the **"One-Thumb Rule"**: Can it be operated with one thumb, while walking a dog, without reading instructions?

### **9.6.3 Risk Communication (The 95% Rule)**

We must explicitly communicate the limitations of AI transparency to the B2B Coaches. We do not promise perfection; we promise resilience. We set the expectation that the AI will be perfect 95% of the time. For the 5% of "Hallucinations" (e.g., AI forgetting a client's dog's name or repeating a phrase), we educate the Coach on how to use the **Operator Mode** to smooth over the error using human humor. We frame these not as "Software Bugs" to be fixed instantly, but as "Relational Hiccups" to be managed personally.
